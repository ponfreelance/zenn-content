行動ログをLLMに渡して「この人は今どの職業に近いか」を判定する機能は、動くものだけなら1日あれば作れる。詰まるのはその後で、結果が日替わりで変わる、JSONが壊れる、無料枠のレート制限で止まる、といった運用側の問題が出てくる。

この記事は、Groqのような低コストのLLMで分類機能を組もうとしていて、動いた後の壊れ方を先に知っておきたい人向けに書いている。

## 結論

壊れやすい箇所は5つあり、対策は次のとおり。

- LLMに渡すのは生ログではなく集計値にする
- 出力は選択肢を固定したJSONにして、受け取り側で検証する
- 判定結果の切り替えには、組み込みのチャタリング対策と同じ不感帯を入れる
- 失敗したら新しい結果を捏造せず、前回の結果を維持する
- 判定は日次バッチにして、キャッシュ前提で組む

以下、なぜ壊れるか、どう組むか、コード例、落とし穴の順に書く。

## 問題の深掘り：なぜ判定が安定しないか

LLMの出力は確率的で、入力が曖昧なほど候補同士の差が小さくなる。

ログが数日分しかないユーザーに「職業を1つ選べ」と聞くと、スコアはほぼ横並びになる。その状態でtemperatureを0にしても、入力が1件増えるだけで1位が入れ替わることがある。ユーザーから見ると、昨日はAだった職業が今日はBになり、明日はまたAになる。

制御をやっている人なら見覚えがある現象だと思う。しきい値付近のアナログ値を比較すると、出力がバタつく。チャタリングと同じ構造で、対策も同じ発想で済む。判定そのものを賢くするのではなく、切り替えの条件を重くする。

この判定は、ユーザーが職業を選ぶドラッグ&ドロップ型ではなく、行動ログから職業が見えてくる観察型にしたかった。そこで自作したのが、副業のcommitとダイエットの歩数を1つのキャラで育てるSaaSの[ALTER](https://alter.ponfreelance.com?utm_source=zenn&utm_medium=article&utm_campaign=alter&utm_content=affiliflow)である。

この種のツールで職業がコロコロ変わると、見守られている感じが消え、責められているような感覚になる。焦らせないことを売りにするなら、判定の安定性は機能の一部として扱うことになる。

## 解決手順

### ステップ1：生ログではなく集計値を渡す

行動ログをそのままプロンプトに入れると、トークンが増え、原価に直接響く。LLMに読ませるのは数字のサマリだけにする。

例えば直近の期間について、ログのある日数、commit数、歩数の合計、食事記録の件数、集中時間の合計を出す。この程度なら数百トークンに収まる設計にできる。日数も一緒に渡しておくと、ログが少ないかどうかを後段で判断しやすい。

### ステップ2：出力を選択肢固定のJSONにする

職業名を自由に書かせると表記ゆれが起きる。システムプロンプトで選択肢を列挙し、JSONだけを返させる。Groqはresponse_formatでJSONモードを指定できる。

受け取り側では、返ってきたjobが選択肢に含まれているか必ず検証する。モデルを信用して、検証なしにDBへ書き込まない。

### ステップ3：切り替えに不感帯を入れる

判定結果をそのまま採用せず、次のルールをかける。

- ログの日数が最小日数に満たないうちは判定を確定しない
- 現在の職業と違う候補が出ても、同じ候補が一定回数続くまで切り替えない

最小日数と連続回数は調整値で、ここでは仮に7日と3回とする。実データを見て詰めることになる。

### ステップ4：失敗したら前回の結果を維持する

APIエラー、JSON破損、選択肢外の値のどれが起きても、ユーザーに見せる職業は変えない。判定が取れなかった日は何も起きなかった日として扱う。

### ステップ5：日次バッチとキャッシュ前提にする

ユーザーが画面を開くたびに判定を呼ぶと、無料枠のレート制限に早く当たる。判定は1日1回のバッチにして、結果は保存したものを返す。

## コード例

動作確認用の最小構成で、本番コードそのものではない。モデル名は変わりやすいので、利用時にGroqの一覧を確認してほしい。

```ts
const JOBS = ["engineer", "writer", "runner", "cook", "scholar", "wanderer"] as const;
type Job = (typeof JOBS)[number];

type Features = {
  days: number;        // ログのある日数
  commits: number;     // 副業
  steps: number;       // 運動
  meals: number;       // 食事記録
  flowMinutes: number; // 集中時間
};

type Verdict = { job: Job; reason: string };

async function askGroq(f: Features): Promise<Verdict | null> {
  const res = await fetch("https://api.groq.com/openai/v1/chat/completions", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.GROQ_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      model: "llama-3.1-8b-instant",
      temperature: 0,
      response_format: { type: "json_object" },
      messages: [
        {
          role: "system",
          content:
            `行動ログの集計から職業を1つ選ぶ。選択肢は ${JOBS.join(",")} のみ。` +
            `{"job":"...","reason":"..."} のJSONだけを返す。`,
        },
        { role: "user", content: JSON.stringify(f) },
      ],
    }),
  });
  if (!res.ok) return null; // 429や5xxは前回維持に倒す

  try {
    const body = await res.json();
    const v = JSON.parse(body.choices[0].message.content);
    return (JOBS as readonly string[]).includes(v.job) ? v : null;
  } catch {
    return null; // JSON破損
  }
}

type State = { current: Job | null; candidate: Job | null; count: number };

const MIN_DAYS = 7;      // 調整値
const SWITCH_AFTER = 3;  // 調整値

function next(s: State, f: Features, v: Verdict | null): State {
  if (f.days < MIN_DAYS || v === null) return s; // 判断しない
  if (s.current === null) return { current: v.job, candidate: null, count: 0 };
  if (v.job === s.current) return { ...s, candidate: null, count: 0 };

  const count = v.job === s.candidate ? s.count + 1 : 1;
  if (count >= SWITCH_AFTER) return { current: v.job, candidate: null, count: 0 };
  return { ...s, candidate: v.job, count };
}
```

nextは純粋な関数にしてあるので、状態遷移だけを単体テストできる。LLMを呼ばずにテストできる形にしておくと、不感帯の挙動を何度でも検証できる。

## 落とし穴と対処

ここに書くのは、件数を数えた運用実績ではない。この構成で壊れやすいと見ている箇所と、先に入れておく対処である。

**集計値が全部ゼロのとき**
ログがまったくない日もある。そのままLLMに渡すと、それらしい職業を返してくる。ゼロ入力はLLMを呼ぶ前に弾き、判定対象から外す。ステップ3の最小日数チェックは、この対策も兼ねている。

**選択肢外の値や表記ゆれ**
JSONモードを指定していても、キーが欠けたり、選択肢にない職業名が返ってきたりする可能性は残る。モードの指定は保険と考え、検証は受け取り側で必ず行う。検証に落ちたら前回維持に倒す。

**レート制限と一時エラー**
無料枠では429が返ってくる前提で組む。その場しのぎで即リトライを重ねると、制限の中でさらに悪化させる。バッチなら、失敗したユーザーだけを後ろに回して間隔を空けて再実行すれば足りる。それでも取れなければ、その日は前回維持で終える。

**入力が増えて原価が読めなくなる**
機能追加のたびに集計項目が増え、プロンプトが膨らんでいくことがある。項目を足すときは、判定にその項目が本当に効くか確かめてからにする。効かない項目はLLMに渡さない。

**判定理由が納得できない**
職業だけを返すと、なぜその職業かがユーザーに伝わらない。reasonを1行返させて、画面に出せる形で保存しておく。ただし理由はLLMが後付けで作る文章でもあるので、判定の根拠そのものとして扱わない。

## まとめ

LLMによる職業判定は、動かすだけなら難しくない。運用で効いてくるのは、入力を集計値に絞ること、出力を検証すること、切り替えに不感帯を入れること、失敗時に前回の結果を維持することの4点だった。

特に不感帯は、組み込みでチャタリング対策をしてきた人なら考え方がそのまま使える。LLMだからといって特別な作法が要るわけではない、というのが自分の実感である。
