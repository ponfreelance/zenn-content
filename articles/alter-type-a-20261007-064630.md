単位も分布も違う数字を1つの値にまとめたい人向けの記事。具体例は GitHub の commit 数と1日の歩数。センサ値のスケール合わせを仕事でやっているC言語エンジニアなら、考え方はそのまま使える。

個人開発で複数のログを1つのスコアにしたい人、ゲーム化した習慣アプリを作りたい人にも向いている。

## 結論

commit と歩数のように単位も分布も違う値は、そのまま足すと片方が全体を支配する。対処は4つある。

- 指標の性質ごとに圧縮方法を変える
- 個人の基準値で割って無次元にする
- tanh などで1日の上限を飽和させる
- 欠測と0を区別して扱う

この記事ではCのサンプルで骨格を示し、そのあと壊れやすい箇所をチェックリストとして並べる。

## 問題の深掘り：なぜ素直に足すと壊れるのか

異種メトリクスをまとめるとき、最初に当たるのは単位と分布の違いだ。commit は1日0件から十数件に収まる離散カウントで、歩数は数千から1万超まで動く連続に近い量になる。単純に足せば歩数が全体を占め、commit は誤差になる。

では0〜1に min-max で潰せばよいかというと、これも崩れやすい。1日だけ突出した日が最大値として基準になり、普段の日がすべて低く見えてしまう。

次に厄介なのが分布の裾の重さだ。commit は初回の import や lockfile の更新、bot の自動コミットで、実作業と無関係に跳ねる。歩数も端末の同期が遅れて、まとめて入ることがある。外れ値が1回入るだけで、その人の基準値が歪む。

さらに、数字を経験値として見せる以上、数字を増やす行動が目的化する。commit を細かく刻めば経験値が増える設計だと、それは作業の記録ではなくなる。

この問題を扱うために、自分は [ALTER](https://alter.ponfreelance.com?utm_source=zenn&utm_medium=article&utm_campaign=alter&utm_content=affiliflow) というツールを作った。副業の commit とダイエットの歩数を1つのキャラで育てる SaaS で、食事=MP、運動=HP、フロー時間=EXP、副業=CHA という対応で指標を持たせている。

以下は、異種の数字を共通の単位に寄せる設計の考え方を、Cのサンプルで整理したものだ。サンプルの係数は説明用の仮値で、ALTER の実装値ではない。

## 解決手順

### ステップ1：指標の性質で圧縮方法を分ける

最初にやるのは、指標を性質で分類すること。

- commit：離散カウントで、裾が重い。対数で圧縮する
- 歩数：連続量で、裾が軽い。基準値との線形比で扱う
- 時間量（集中した時間など）：連続量で、1日の物理的な上限がある。線形比で扱う

全部に同じ変換をかけると、どれかが潰れる。たとえば歩数に対数をかけると、3000歩と12000歩の差がほとんど出なくなる。commit に線形比をかければ、bot が100件入れた日に基準が壊れる。

### ステップ2：日付境界を先に決める

指標を日次バケットに揃える。ここを曖昧にすると、あとで原因の分からないズレになる。

GitHub の commit は UTC で保存され、author date にはオフセットが付く。歩数はヘルスケア側が端末のローカル日で集計していることが多い。ユーザーのタイムゾーンを1つ決め、その基準で1日を切って両方を同じ日に載せる。深夜に作業する人ほど、この差が表に出る。

### ステップ3：個人の基準値で割る

他人との比較には使わない。その人自身の基準値で割って、無次元の量にする。

基準値は、直近28日のうちデータが取れた日だけの中央値を想定している。平均は外れ値に引っ張られるので避ける。履歴が少ない最初の1週間は固定の初期値で始め、データが貯まった時点で個人値に切り替える。

### ステップ4：飽和させる

無次元にした値を tanh に通し、1日に積める経験値に上限をつける。上限に近づくほど増え方が鈍るので、1日に何百件 commit しても、何万歩歩いても、積めるのは上限までになる。

上限の存在は、水増しを割に合わなくする効果と、片方の指標が支配するのを防ぐ効果を兼ねている。

### ステップ5：重みをつけて合算し、累積だけにする

指標ごとの1日の上限が、そのまま重みの意思表示になる。副業を優先したいなら commit 側の上限を大きくする。

合算した日次の値は累積に足すだけで、減算はしない。この点は「壊れやすい箇所」の節でもう一度触れる。

## コード：Cでの骨格

説明用の最小構成。

```c
#include <math.h>
#include <stdbool.h>

typedef enum { MODE_LOG, MODE_LINEAR } Mode;

typedef struct {
    double value;    // その日の生の値
    bool   present;  // 取得できたか（0 と欠測を分ける）
} DailyMetric;

typedef struct {
    Mode   mode;
    double baseline; // 個人の基準値（中央値など）
    double cap;      // 1日に積める経験値の上限
} Config;

// 圧縮 → 基準値で割る → tanh で飽和
static double normalize(const DailyMetric *m, const Config *c)
{
    if (!m->present || c->baseline <= 0.0) {
        return 0.0; // 欠測は加算しない（罰もしない）
    }

    double x;
    if (c->mode == MODE_LOG) {
        x = log1p(m->value) / log1p(c->baseline);
    } else {
        x = m->value / c->baseline;
    }
    return c->cap * tanh(x);
}

double daily_xp(const DailyMetric *commits, const DailyMetric *steps)
{
    static const Config cfg_commit = { MODE_LOG,    3.0,    60.0 };
    static const Config cfg_steps  = { MODE_LINEAR, 6000.0, 40.0 };

    return normalize(commits, &cfg_commit)
         + normalize(steps,   &cfg_steps);
}
```

仮値で計算すると、挙動はこうなる。

- commit が12件の日は約57、120件の日は約59.9。10倍の差が、経験値では3程度にしかならない
- 歩数が3000歩の日は約18.5、6000歩で約30.5、12000歩で約38.6。歩いた分だけ素直に増えるが、上限は超えない

基準値に到達した日（x=1）は、上限の約76%になる。この「基準を満たせば7〜8割もらえる」感覚は、焦らせない設計と相性がいい。上限ぎりぎりを狙う動機が生まれにくい。

## 落とし穴と対処

ここに挙げるのは、運用ログから拾った事例ではなく、この種の統合で壊れやすい箇所を設計時に潰すための項目だ。

**1. 初回 import と bot の大量 commit**
リポジトリを取り込んだ日や、依存更新の bot が動いた日に commit 数が跳ねる。対数圧縮と飽和で影響を丸めたうえで、bot の author を集計から外す。merge commit を数えるかどうかも、先に決めておく。

**2. 日付境界のずれ**
commit は UTC、歩数はローカル日という食い違いで、同じ日の活動が別の日に落ちる。ステップ2のとおり、ユーザーのタイムゾーンで両方を切り直す。

**3. 欠測と0の混同**
歩数が未同期の日と、本当に歩かなかった日は別物だ。present フラグで区別し、欠測日は基準値の計算からも除く。欠測を0として中央値に入れると、基準値が下がって翌日以降の経験値が水増しされる。

**4. 履歴の書き換え**
squash や force push で、あとから commit 数が変わる。日次の値を後から再計算すると、過去の経験値が減る日が出てくる。一度加算した日は確定させ、後から減算しない方針がいい。多少の増減のズレより、積んだものが減る体験のほうが害が大きい。

**5. 基準値の追従で頑張りが報われなくなる**
基準値を直近の実績から作ると、頑張った月の翌月は基準が上がり、同じ行動で得られる経験値が減る。基準値の更新幅に上限を設け、更新の頻度も週単位に絞って、急に動かないようにする。

**6. 水増し**
commit を細かく刻めば経験値が増えるなら、数字稼ぎに走る人が出る。日次の飽和上限が最初の防波堤になる。それでも抜ける分は、記録の目的が自分の歩みの把握であって点数稼ぎではないと、画面の言葉で示すしかない。

**7. 連続記録の断絶**
ストリーク（連続日数）を前提にすると、1日休んだだけで積み上げが消えたように見える。累積だけを見せ、休んだ日を罰しない設計にしておけば、再開の心理的な負担が小さい。習慣化アプリで多い離脱パターンの一つがここだと考えている。
