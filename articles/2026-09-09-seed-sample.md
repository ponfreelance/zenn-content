C言語23年、自分はフリーランスで組み込みのコードレビューに入ることが多いです。今回は「サンプル集」と呼べるくらい小さい38行のコードを題材に、creviewが何を拾って何を拾わなかったかを行番号ベースで検証します。手動レビューだと、3項演算子や論理否定でのNULLチェックのような「一見安全に見える書き方」の周辺を読み飛ばしやすく、逆に見た目が危なそうな箇所ばかりに時間を使ってしまう傾向があります。検出結果は5件、うち2件がNULLチェック関連でした。

## この記事の前提（SCQA）

- **状況**: 38行程度の短いコードでも、NULLチェック漏れ・未初期化変数・危険な再帰・マジックナンバーが同時に混在します。レビューワは全部を均等に見ているつもりでも、実際には目が止まる箇所に偏ります。
- **問題**: 手動レビューでは「bad_null」のようにいかにも危なそうな名前の関数には注意が向きますが、「ternary_null_check」のように名前に安全そうな単語が入っている関数は、中身を読まずに通過させやすいです。今回のケースでも、3項演算子でNULLチェックしているように見える関数にNULL未検査の指摘が出ています。
- **問い**: 名前や見た目の印象に引きずられずに、全関数のNULL契約・初期化状態・再帰構造を均等にチェックするには、レビューのどの部分を機械に渡すべきか？
- **答え**: creviewでNULL契約・未初期化・自己再帰・マジックナンバーの4系統を機械的に洗い出し、人間は「本当にNULLが来ないと言い切れるか」というドメイン判断だけに時間を使う分業にしました。

## L0: まずコンパイラ警告を全部潰す

creviewの話に入る前に、`-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）または`-Wall -Wextra -Werror -Weverything`（Clang）を有効にしてビルドが通るか確認してください。未初期化auto変数の読み出し、自明なNULL deref、戻り値破棄、switch case抜けは現代のコンパイラが標準で拾います。

実際、今回の`bad_uninit()`の`int y = x + 1;`（未初期化のxを使用）は、多くの環境で`-Wuninitialized`が反応する典型パターンです。これがビルドで警告ゼロにならないPRは、creviewを走らせる前にそもそもレビュー対象にしないルールにしてしまうのが第一手です。creviewはL0を通過した後の「コンパイラが黙っているが危険なパターン」を拾うためのレイヤーだと考えてください。

## 検証用コード

```c
// NULL未チェック
void bad_null(int *p) {
    *p = 42;
}

// 未初期化変数
void bad_uninit() {
    int x;
    int y = x + 1;
}

// goto使用
void bad_goto() {
    goto end;
    end:;
}

// 再帰
int bad_recursive(int n) {
    return bad_recursive(n - 1);
}

// 安全な関数
int good_func(int *p) {
    if (p == NULL) return -1;
    return *p;
}

// 3項演算子でのNULLチェック（安全）
int ternary_null_check(int *p) {
    return p ? *p : -1;
}

// 論理否定でのNULLチェック（安全）
int logical_not_check(int *p) {
    if (!p) return -1;
    return *p;
}
```

## CWE/MISRA マッピング

| 検出行 | パターン | CWE | 事故の形 |
|-------|---------|-----|---------|
| L2 (bad_null) | NULL契約未表明（nonnull属性なし） | CWE-476 | 呼び出し側がNULLを渡すとその場でクラッシュ。契約が型で表現されていないため、呼び出し側のミスをコンパイル時に弾けない |
| L3 (42) | マジックナンバー | CWE-547 | 42が何を意味するか分からず、仕様変更時に該当箇所を探し出せない。保守コストの温床 |
| L9 (bad_uninit) | auto変数の未初期化使用 | CWE-457 | xは不定値。y = x + 1の結果は実行環境・最適化レベルで変わり、再現困難なバグの原因になる |
| L19 (bad_recursive) | 深さ制限なし自己再帰 | CWE-674 | nが負や大きい値のとき無限に近い再帰でスタックオーバーフロー。組み込みでは即クラッシュに直結 |
| L30 (ternary_null_check) | NULL契約未表明（nonnull属性なし） | CWE-476 | 3項演算子でp自体はチェックしているように見えるが、関数シグネチャ上はNULL可の契約が明示されておらず、呼び出し側は「NULLを渡してよい関数」として扱ってしまう |

なお`logical_not_check()`（L36〜39）は今回の検出結果5件には含まれていません。`if (!p) return -1;`で明示的にNULL分岐しているため、creviewのNULL検査ロジック上はチェック済みと判定されたと考えられます。同じ「NULLチェックしているように見える」書き方でも、3項演算子側は指摘され、if文側は指摘されない、という差が出ている点は手動レビューでも見落としやすいところです。

## creview の使い方（CLI 実行例）

```
L2 【重大】: ATTR-NONNULL-001: bad_null() の p を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L3 【保守危険】: マジックナンバー42 (リテラル) — allowlist 外。#define / enum / .creviewrc.json で命名 or 許可
L9 【重大】: 未初期化変数xを使用(8行目で宣言、初期化なし)。不定値
L19 【保守危険】: 関数bad_recursiveが自己再帰。深さ制限なしでスタックオーバーフローの危険
L30 【重大】: ATTR-NONNULL-001: ternary_null_check() の p を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
```

3段階ラベルの読み方は次の通りです。

- **【重大】**: NULL未検査や未初期化変数のように、実行時にクラッシュや不定動作へ直結する箇所。今回はL2・L9・L30の3件で、全体5件のうち過半数を占めています。
- **【設計不明】**: 今回の検出結果には出ていませんが、意図的な設計かバグか機械では判定できないパターンに付くラベルです。goto（L13〜15）はこのコードでは前方ジャンプのみで危険パターンに該当せず、検出対象外になっています。
- **【保守危険】**: マジックナンバーや自己再帰のように、即クラッシュはしないが将来の変更・移植で事故る可能性が高い箇所。L3とL19が該当します。

実行コマンドは目的に応じて出し分けます。PRのdiffだけ見たい場合は`--preset pr`、セキュリティ観点を強めたい場合は`--preset security`、CIにそのまま食わせる場合は`--format sarif`を使う想定です。

## 3段階の使い分け

| 場面 | 使うツール | 使いどころ |
|------|-----------|-----------|
| L0: ビルド時（まずここ） | gcc / clang の警告 + `-Werror` | `-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）/ `-Weverything -Werror`（Clang）。警告ゼロにならないPRはそもそもレビューに入らないルール化 |
| L1: PRチェック | clang-tidy / cppcheck | OSSの主流チェックをCIで強制 |
| L2: PRレビュー | 自社プロダクトcreview（CLI） | L2・L30のようなNULL契約漏れ、L9の未初期化、L19の自己再帰をdiffベースで拾う。severityモデル（重大/設計不明/保守危険）付き |
| L2': 自己チェック（PR投げる前） | 自社プロダクトc-review-ai（ブラウザ版） | 環境構築なしで今回のような短いコード片を貼って即確認できる |
| L3: チーム監査・MISRA準拠 | 自社プロダクトCSAF | プロジェクト全体でNULL契約・マジックナンバーのallowlist運用状況を横断的に監査 |

失敗談としては、`ternary_null_check`のような書き方を「NULLチェックしてあるから安全」と自分の目でも一度スルーしかけたことがあります。3項演算子の中でpを評価している事実だけを見て、関数シグネチャ側にnonnull契約がないという別軸の問題を見落としていました。creviewの検出結果を見て初めて、「チェックの有無」と「契約の明示の有無」は別レイヤーの話だと意識し直しました。

## まとめ

- 検出5件のうち3件が【重大】（L2・L9・L30）で、NULL契約未表明が2件、未初期化変数が1件という内訳でした。
- 同じ「NULLチェックしているように見える」書き方でも、3項演算子（L30）は指摘され、if文＋論理否定（L36〜39）は指摘対象から外れており、書き方によって検出粒度が変わる点は把握しておく必要があります。
- マジックナンバー（L3）と自己再帰（L19）は【保守危険】止まりで、即座に落ちるバグではないため手動レビューで後回しにされがちな箇所です。
- gotoの使用（L13〜15）は前方ジャンプのみで今回は検出対象外であり、goto=即危険という単純な扱いはしていません。
- L0のコンパイラ警告（未初期化変数など）を先に潰した上で、creviewはL0を通過した後のNULL契約・再帰構造・マジックナンバーという「コンパイラが黙る領域」に絞って使うのが実務的です。
