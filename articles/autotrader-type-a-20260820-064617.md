バックテストで年利何十%と出ていたロジックを本番投入したら、初月で赤字になった経験がある人は少なくないはずだ。俺自身、自作の自動売買ツールで似たようなことを経験した。原因は大きく3つ、手数料・スリッページ・部分約定に集約される。この記事ではそれぞれがなぜ起きるのか、どう検証に組み込むかを実装レベルで書く。

## 結論から言うと

バックテストと本番の乖離は、大半が「約定を理想化しすぎている」ことに起因する。手数料を後から引き算するだけの実装、スリッページをゼロ前提で計算するロジック、指値が100%約定する前提のシミュレーション。この3つを潰すだけで、体感の乖離幅はかなり縮む。逆に言えば、この3つを検証コードに組み込んでいないバックテストは、数字自体があまり意味を持たない。

以下、それぞれの原因と対処を順に見ていく。

## なぜ乖離が起きるのか

バックテストは基本的に「過去の価格データに対して、条件を満たしたら約定した体で計算する」仕組みだ。ここに罠がある。過去データは基本的に**約定価格そのもの**であって、自分が出した注文がどこで刺さったかではない。

例えば1分足の終値でエントリー判定をして、同じ終値で約定した体にするロジックはよく見かける。だが実際の取引所では、その終値が出た瞬間に注文を出しても、板の状況によっては数tick先でしか約定しない。この差が積み重なると、月間で見たときに数%の乖離になる。

手数料についても同様で、Maker/Takerで手数料率が変わる取引所は多い。GMOコインとbitFlyerでは手数料体系が違うし、Zaifのように取引量によって手数料が変動する仕組みもある。バックテストで一律0.1%として計算していると、実際の取引回数が多い高頻度戦略ほど誤差が拡大する。

自分は最初、この検証の甘さに気づかず、5取引所分の実装を横断して同じ約定モデルを使い回していた。結果、Zaifだけ手数料の実装が違うことに気づかず、2週間分のログを見直す羽目になった。こういう取引所ごとのクセを吸収する設計を最初からやっておけばよかったと今は思う。この手の実装をまとめて学べるように[AutoTrader 実装学習キット](https://autotrader.ponfreelance.com/sales/?utm_source=zenn&utm_medium=article&utm_campaign=autotrader&utm_content=affiliflow)というキットを作った。5取引所分のAPI連携サンプルと、約定モデルの実装例が入っている。

## 解決手順

### 手順1：手数料を取引所ごとに実装で分離する

まず手数料を「一律のパラメータ」として扱うのをやめる。取引所ごとにMaker/Taker手数料が違うので、注文タイプ（指値か成行か）と取引所名の組み合わせで手数料テーブルを持つ。

具体的には、注文執行のロジックの中に手数料計算を埋め込むのではなく、独立した関数として切り出す。バックテストと本番の両方から同じ関数を呼ぶようにしておけば、少なくとも「バックテストだけ手数料計算が甘い」という事故は防げる。

自分の場合、最初はバックテスト用に別の手数料計算スクリプトを書いていて、本番用のコードとロジックが少しずつズレていった。3ヶ月くらい経った頃に気づいたら、バックテスト側は税抜き手数料、本番側は税込みで計算していて、月次の乖離が0.3%くらい発生していた。金額にすると大した額ではないが、これが積み重なると年間でのパフォーマンス評価を誤らせる。

### 手順2：スリッページをランダムではなく分布でモデル化する

スリッページを「固定値を引く」だけで済ませているバックテストをよく見かける。例えば「0.05%を毎回引く」という実装だ。これは無いよりましだが、実際の値動きが荒い時間帯（指標発表直後など）は、スリッページがその何倍にもなることがある。

自分が実装したのは、過去の出来高データからボラティリティを推定し、ボラティリティが高い時間帯ほどスリッページの分布を広くとる方式だ。完璧なモデルではないが、固定値よりは実態に近づく。週3時間くらいかけてこの部分のロジックを見直したことで、バックテストの利益率が本番実績に対して15%近く近づいた実感がある。

ここで重要なのは「スリッページをゼロにする」方向で戦略を組まないことだ。むしろスリッページが乗っても勝てる戦略かどうかを、バックテストの段階で確認する。スキャルピング系の戦略ほどここで死ぬ。

### 手順3：部分約定を前提にポジション管理を作る

これが一番見落とされがちだ。バックテストでは「指値を出したら全量約定する」という前提で書かれていることが多いが、本番では板が薄い通貨ペアや時間帯だと、指値の一部しか約定しないことがある。

部分約定が起きると何が困るかというと、ポジションサイズの計算がズレる。例えば1BTC分の指値を出して0.3BTCしか約定しなかった場合、残り0.7BTCの注文をキャンセルするのか、そのまま残すのか、成行に切り替えるのかで結果が大きく変わる。この分岐をバックテストに組み込んでいないと、本番で想定外の建玉を抱えることになる。

自分はここで一度、想定より小さいポジションで利確ラインに到達し、想定していた利益の半分以下しか出なかったことがある。原因を追ったら、部分約定後の残数量処理が本番コードにだけ実装されていて、バックテスト側では「全量約定した体」で損益計算していたことが分かった。この手の食い違いは、コードレビューだけでは気づきにくい。

## コード例：約定モデルの骨格

言語はPythonで書くが、考え方自体はC言語の組み込み制御でイベント駆動を書く感覚に近い。状態を持つステートマシンとして注文処理を実装する。

```python
from dataclasses import dataclass
from enum import Enum

class OrderStatus(Enum):
    PENDING = "pending"
    PARTIAL = "partial"
    FILLED = "filled"
    CANCELLED = "cancelled"

@dataclass
class FeeModel:
    maker_fee: float
    taker_fee: float

    def calc(self, price: float, qty: float, is_maker: bool) -> float:
        rate = self.maker_fee if is_maker else self.taker_fee
        return price * qty * rate

@dataclass
class Order:
    order_id: str
    price: float
    qty: float
    filled_qty: float = 0.0
    status: OrderStatus = OrderStatus.PENDING

    def apply_fill(self, fill_qty: float):
        self.filled_qty += fill_qty
        if self.filled_qty >= self.qty:
            self.status = OrderStatus.FILLED
        elif self.filled_qty > 0:
            self.status = OrderStatus.PARTIAL

    def remaining(self) -> float:
        return self.qty - self.filled_qty
```

このように、注文には「部分約定中」という状態を明示的に持たせる。バックテスト側でもこのクラスをそのまま使い回すことで、本番との実装差分を減らせる。手数料もMaker/Takerを注文の性質（指値が板に残ったか、成行で即約定したか）に応じて切り替える。

取引所ごとのクセ、例えばZaifで`order_id=0`が返ってくる仕様のように、レスポンスの形式そのものが特殊なケースは、この骨格の外側にアダプター層を作って吸収するのがいいと思う。取引所固有の挙動をコアロジックに混ぜ込むと、5取引所対応した頃には条件分岐が読めなくなる。

## 落とし穴と対処

ここで一つ、実際にハマった話を書く。bitFlyerのAPIには短時間に連続してリクエストを送るとRate Limitに引っかかる仕様がある。バックテストでは当然この制限は存在しないので、本番で初めて「注文が通らない」という事象に遭遇した。

原因を調べたら、複数の判定ロジックが同時にAPIを叩く設計になっていて、1秒間に想定以上のリクエストを送っていた。対処としては、リクエストをキューに積んで一定間隔で処理する仕組みを入れた。この実装に3日くらいかかったが、Rate Limit回避の実装例がネット上にほとんど無く、公式ドキュメントとにらめっこしながら手探りで直した記憶がある。

もう一つ、複数APIを連携させるアプリだと状態管理が想像以上に複雑になる。5取引所同時運用のとき、片方の取引所でネットワークエラーが起きた際に、もう片方のポジションだけ更新されて整合性が崩れたことがあった。この手の異常検知は後回しにされがちだが、実際に事故が起きてから直すと被害が大きい。
