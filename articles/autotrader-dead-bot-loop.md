自分は自社プロダクトとして暗号資産の自動売買BOT（AutoTrader）を開発・運用しています。バックエンドは FastAPI + APScheduler、Oracle Cloud の無料枠 VM（メモリ 954MB）で常時稼働という構成です。

2026年8月2日、稼働中のBOTのうち AI 戦略の1本が 21:01 を最後に実行を止めました。気づいたきっかけは監視アラートです。ログを追うと、単に止まったのではなく、再起動のたびに「復帰しては dead 判定されてスケジューラから外される」を繰り返す、永久 dead ループになっていました。

原因は2つのバグの合わせ技でした。この記事はその調査の記録です。結論だけ先に書くと、

- 5分毎の強制 `gc.collect()` が、スワップ環境で WORKER TIMEOUT の連鎖を引き起こしていた
- dead 復帰処理が `last_run_at` を古いまま残すため、実行間隔が dead 閾値に近い BOT だけ「復帰した瞬間にまた dead 判定される」競合を踏んでいた

の2つです。

## 最初の仮説は「またメモリリークか」

このシステムは元々 Render で動かしていて、Oracle に移した理由の一つがメモリでした。その経験があったので、今回も反射的に「またメモリだろう」と当たりをつけて調査に入りました。

この仮説は半分だけ合っていました。メモリ圧は確かに関与していたのですが、BOT が復帰しない直接の原因は別にありました。最初の思い込みのせいで、スケジューラ側の競合を疑うのが後回しになっています。

## バグ1: 善意の gc.collect() が worker を殺していた

スケジューラには、メモリ対策のつもりで5分毎に `gc.collect()` を打つ処理を入れてありました。

954MB の VM でヒープの一部がスワップに追い出された状態でフル GC を打つと、GC がスワップ上のオブジェクトまで総なめするのでスラッシングが起きます。イベントループが数分単位で停止し、gunicorn が worker を kill、プロセス再起動で全 BOT が巻き添えになる。この連鎖が 8/1〜8/2 の2日間で3回起きていました。

対処は `gc.collect()` の削除です。正直に書くと、頻度を下げる・メモリを増やすといった代替案と比較検討したわけではなく、「引き金になっているものをまず外す」以上の理由はありません。GC は CPython の世代別自動収集に任せることにしました。

## それでも1本だけ復帰しない

GC を消して worker の連鎖 kill は止まりましたが、AI 戦略の BOT（実行間隔 15分）だけが復帰しませんでした。1分間隔の BOT は普通に動いている。「全部死ぬ」なら再起動やリソースを疑えばいいのですが、「特定の1本だけ、再起動のたびに死ぬ」のです。

## journalctl の7秒差

journalctl を時刻で突き合わせて、ようやく競合が見えました。

```
23:47:33  dead 判定（last_run_at が閾値 31分を超過）
23:47:40  初回ジョブ到着
```

7秒差です。

このシステムは `last_run_at` が31分更新されない BOT を dead と判定して unschedule します。そして再起動時の復帰処理は、status を dead → running に戻すだけで **`last_run_at` を古いまま残して** いました。すると、

- **15分間隔の BOT**: 復帰後の初回ジョブは15分後に来る。一方 dead 判定は古い `last_run_at` 基準なので、復帰の直後にはもう閾値31分を超えている。**dead 判定が先に勝つ**
- **1分間隔の BOT**: 初回ジョブが60秒で来て `last_run_at` が更新される。罠にかからない

「間隔の長い BOT だけが、再起動のたびに死ぬ」見え方の正体はこれでした。復帰しては7秒後に dead 判定されて unschedule、を延々と繰り返していたわけです。

## 修正

復帰処理を `revive_dead_bots()` として切り出し、`last_run_at` のリセットを足しました。

```python
def revive_dead_bots(db) -> list[Bot]:
    dead_bots = db.query(Bot).filter(Bot.status == "dead").all()
    for bot in dead_bots:
        bot.status = "running"
        bot.last_run_at = datetime.now(UTC)  # これを忘れると dead 判定との競合が残る
    db.commit()
    return dead_bots
```

回帰テストを2件書いて、1分間隔 BOT の挙動が変わらないことも確認しています。

## 再発防止をどこで止めるか

スケジューラ側の競合は再現条件まで特定できたので修正して閉じました。一方メモリ側は「`gc.collect()` が引き金」までは分かりましたが、そもそもヒープがスワップに追い出されるほど太る要因が確定したとは思えませんでした。

要因が確定していない段階で修正を重ねるのはやめて、毎朝のログレビューに worker の RSS と swap 使用量の観測項目を足すだけにしています。肥大が再発の前兆として数字に出るはずなので、出てから次を考えます。

## 学び

- **過去の障害経験は仮説を引っ張る。** 「前もメモリだったから今回もメモリ」で入ったせいで、スケジューラの競合を疑うのが遅れた
- **復帰処理は状態を全部戻す。** status だけ戻してタイムスタンプを戻し忘れると、閾値ぎわの設定の BOT だけが競合を踏む。全滅しないぶん、かえって気づきにくい
- **要因が確定しないうちは、直しを重ねるより観測を足す。** 直した気になるのが一番怖い
