C言語23年、自分はフリーランスで組み込みのコードレビューに入ることが多いです。

レガシーの保守案件でよくあるのが、「動いているから触るな」と言われている関数です。`strcpy` や `sprintf` が並んでいても、長年本番で動いてきた実績があると、直す提案自体が通りにくい。今回の `copy_name` / `format_path` / `wipe_buffer` / `read_at` はどれもこのタイプの典型で、名前だけ見ると単純なユーティリティですが、中身は境界チェック無しのコピーとポインタの sizeof 誤用が同居しています。既存コードに静的解析を当てるときは「全部直す」ではなく「どこから手を付けても壊れない順」を決める作業が先に来ます。

## この記事の前提（SCQA）

- **状況**: レガシーコードは「動いている」という実績が既にあるので、リファクタの提案よりも先に「触って壊れないか」が判断基準になります。
- **問題**: `strcpy` や `sizeof(p)` のような危険パターンは目視で気づけますが、関数呼び出し側の契約（NULL を渡していいか、境界チェックは呼び出し元の責任か）は関数単体を読むだけでは分かりません。直す優先順位を決めるための「危険度の内訳」が要ります。
- **問い**: 触るのが怖い既存コードに対して、どの粒度で静的解析を当てれば「直していい箇所」と「仕様として残すべき箇所」を分けられるか。
- **答え**: creview の severity ラベルと CWE マッピングを使い、まず「事故になる書き込み・境界外アクセス」を最優先で潰し、NULL 契約の未表明は `__attribute__((nonnull))` で明示するところから着手する、という段階を踏みました。

## L0: まずコンパイラ警告を全部潰す

creview の話に入る前に、`-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）または `-Wall -Wextra -Werror -Weverything`（Clang）を有効にしてビルドが通るか確認します。NULL 引数を nonnull 関数に渡す、未初期化 auto 変数を読む、戻り値を破棄する、自明な NULL deref、use-after-free、境界外配列アクセス（静的決定可なもの）、switch case 抜け、これらは現代のコンパイラが標準で拾います。

レガシーコードの場合、この段階で警告が大量に出て身構えることが多いです。ただし、警告ゼロにならない状態のまま creview のような追加ツールを回しても、コンパイラで拾える指摘まで人間が読み直す羽目になり、レビューの時間配分がおかしくなります。まず L0 を通してから L2 に進む、という順序をレガシー案件ほど徹底したほうが安全です。

## 検証用コード

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* スタックバッファのオーバーフロー（strcpy + sizeof 誤用） */
void copy_name(const char *src) {
    char buf[16];
    strcpy(buf, src);                    /* 検出すべき: 長さ未検証 */
    printf("name=%s\n", buf);
}

/* sprintf による境界未検証 */
void format_path(const char *dir, const char *file) {
    char path[32];
    sprintf(path, "%s/%s", dir, file);   /* 検出すべき: snprintf を使うべき */
}

/* sizeof(ptr) ハマりパターン */
void wipe_buffer(char *p) {
    memset(p, 0, sizeof(p));             /* 検出すべき: sizeof(p) は常に 8（ポインタサイズ） */
}

/* 配列インデックス未検証（scanf 入力をそのまま添字に） */
void read_at(int *arr) {
    int i;
    scanf("%d", &i);
    printf("%d\n", arr[i]);              /* 検出すべき: i の上下限チェック無し */
}
```

## CWE/MISRA マッピング

| 行 | 検出パターン | CWE | 事故の形 |
|----|------------|-----|---------|
| L8 | `strcpy(buf, src)` 長さ未検証 | CWE-121 | スタックバッファオーバーフロー。src が buf[16] を超えるとリターンアドレス破壊 |
| L15 | `sprintf(path, ...)` 出力長未検証 | CWE-121 | dir/file の結合長が path[32] を超えると隣接メモリ破壊 |
| L20 | `sizeof(p)` をポインタに適用 | CWE-467 | 配列長のつもりでポインタサイズ（4/8byte）を渡し、memset の対象範囲が意図と乖離 |
| L20 | p の NULL 未検証で memset | CWE-476 | NULL ポインタ渡しでクラッシュ |
| L27 | scanf 入力を境界チェックなしで添字使用 | CWE-129 | 配列外の任意アドレス読み取り |
| L6, L13, L19, L24 | NULL 契約未表明（nonnull 属性なし） | CWE-476 周辺 | 呼び出し側が NULL を渡していいかどうかが型シグネチャから読み取れない |
| L7, L14 | バッファサイズのマジックナンバー（16, 32） | CWE-547 | サイズ変更時に他の参照箇所を見落とす保守事故 |

## creview の使い方（CLI 実行例）

```
L6 【重大】: ATTR-NONNULL-001: copy_name() の src を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L7 【重大】: マジックナンバー16 (バッファサイズ) — allowlist 外。#define / enum / .creviewrc.json で命名 or 許可
L8 【重大】: strcpy使用。コピー元長未検証でオーバーフロー可能
L13 【重大】: ATTR-NONNULL-001: format_path() の dir を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L14 【重大】: マジックナンバー32 (バッファサイズ) — allowlist 外。#define / enum / .creviewrc.json で命名 or 許可
L15 【重大】: sprintf使用。出力バッファ長未検証でオーバーフロー可能
L19 【重大】: ATTR-NONNULL-001: wipe_buffer() の p を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L20 【重大】: pのNULL未検証でmemset実行。NULLポインタ渡しでクラッシュ
L20 【重大】: sizeof(p)は関数パラメータの decay でポインタサイズ(4/8byte)を返す。配列長は別引数で受け取れ
L24 【重大】: ATTR-NONNULL-001: read_at() の arr を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L27 【重大】: 外部入力iを境界チェックなしで配列添字に使用。範囲外アクセス
```

3段階ラベルの読み方は以下の通りです。

- **【重大】**: 実行時に事故が起きる、または起き得るパターン。今回は全11件がこれに該当し、strcpy/sprintf のオーバーフロー、sizeof(p) の誤用、境界外添字が並びます。
- **【設計不明】**（今回は0件）: バグと断定できないが意図が読めないコード。関数の責務が曖昧な場合などに出ます。
- **【保守危険】**（今回は0件）: 今すぐ壊れないが将来の変更で壊れやすい構造。マジックナンバーは severity 次第でここに落ちることもありますが、今回はバッファサイズという実害に直結する文脈なので【重大】に分類されています。

今回のログで自分が最初に見誤りかけたのは L20 です。「NULL 未検証」と「sizeof(p) 誤用」が同じ行に2件出るため、片方を直せば済むと錯覚しがちですが、これは別々の契約違反です。NULL チェック（あるいは nonnull 属性）と、配列長を別引数で受け取る設計変更は、どちらか一方をやっても他方の事故を防げません。

もう一点、L7・L14 のマジックナンバー指摘は、バッファ宣言の `char buf[16]` と `char path[32]` に対して出ています。ここは配列宣言であって、ポインタの sizeof 誤用（L20）とは別種の指摘です。同じ「16」「32」という数字でも、宣言側のサイズ指定なのか、コピー先の実際の受け皿サイズ検証漏れなのかで意味が違うので、allowlist に単純に数値を足して黙らせるのではなく、`#define BUF_LEN 16` のように命名してから許可リストに載せる方が保守性は上がります。

## 3段階の使い分け

| 場面 | 使うツール | 使いどころ |
|------|-----------|-----------|
| L0: ビルド時（まずここ） | gcc / clang の警告 + `-Werror` | `-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）/ `-Weverything -Werror`（Clang）。警告ゼロにならない PR はそもそもレビューに入らないルール化 |
| L1: PR チェック | clang-tidy / cppcheck | OSS の主流チェックを CI で強制 |
| L2: PR レビュー | 自社プロダクト creview（CLI） | プロジェクト固有パターン、日本語ナレッジ、severity モデル（重大/設計不明/保守危険）、CWE/MISRA マッピング、`--preset pr` で diff のみ、AI 補強 |
| L2': 自己チェック（PR 投げる前） | 自社プロダクト c-review-ai（ブラウザ版） | 環境構築不要、コピペで試せる軽量版。触るのが怖い関数を直す前に、まず単体で投げて反応を見る |
| L3: チーム監査・MISRA 準拠 | 自社プロダクト CSAF | libclang AST + 依存グラフで risk A/B/C 自動昇格。レガシー全体の危険度マップを作る場面 |

レガシー保守の文脈では L2' の使い方が地味に効きます。触るのが怖い関数をいきなり PR に出す前に、ブラウザ版で単体の反応を見て、直す範囲を絞り込んでから CLI 版で diff に対して `--preset pr` を回す、という順序を踏むと、レビューする側もされる側も「この PR は何を直したのか」が説明しやすくなります。

## まとめ

- 今回の11件は全て【重大】に分類され、実害が明確な CWE-121（strcpy/sprintf）、CWE-467（sizeof(p) 誤用）、CWE-476（NULL 未検証）、CWE-129（境界外添字）、CWE-547（マジックナンバー）に対応しています。
- L20 のように同一行に複数の指摘が出た場合、片方を直せば済むと錯覚しやすいので、NULL チェックと配列長の設計変更は別問題として扱う必要があります。
- マジックナンバー指摘（L7, L14）は配列宣言のサイズであり、ポインタの sizeof 誤用とは別種の指摘なので、数値だけ見て同じ対処をしないことです。
- レガシー保守では「全部直す」より先に「事故になる書き込み・境界外アクセス」を優先し、NULL 契約の未表明は `__attribute__((nonnull))` で明示するところから着手すると、既存の呼び出し側を壊さずに進められます。
- L0 のコンパイラ警告を通していない状態で creview を回すと、コンパイラで拾える指摘まで人間が読み直すことになるため、レガシー案件ほど L0 を先に固める順序が効きます。

C言語の静的解析を、いきなり有料ではなく「無料で手を動かす → 日常運用 → 監査レベル」の順で用意しています。

- **まずブラウザで試す → c-review-ai**（自社プロダクト / MIT / 無料）
  貼り付けた1ファイルをその場でレビュー。導入ゼロで挙動を確かめる用。
  → https://cutt.ly/1yuTys1c
- **CLI で日常運用 → creview**（自社プロダクト / 無料）
  手元のコードをコミット前に単発チェック。CI にも組み込める。
  → https://cutt.ly/syuTpB7z
- **リポジトリ全体を監査 → CSAF**（自社プロダクト / ¥4,980 買い切り）
  MISRA 準拠チェックと CWE データフロー解析をリポジトリ横断で走らせ、監査レポート（HTML）を出力。
  レビューの属人化を止めたいチーム向けで、商用の静的解析ツールなら数十万円かかる基本機能を、個人でも入れられる価格にしています。
  → https://cutt.ly/ItKo4MPY

無料の2つで「使える」と感じたら、リポジトリ全体に監査を回すのが CSAF です。バージョンは随時更新しています。
