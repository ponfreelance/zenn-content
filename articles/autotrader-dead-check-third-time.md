前回、自社プロダクトの暗号資産自動売買BOT（AutoTrader）が再起動のたびに死ぬ話を書きました。原因は「dead 判定の基準になる `last_run_at` が古いまま残り、BOT が最初のサイクルを回すより先に『応答なし』と判定される」という競合でした。

修正して、直ったと思っていました。

5日後、同じことが起きました。しかも記事に「再発防止をどこで止めるか」という節まで書いた直後です。

この記事は、同じバグを3回直した話と、3回目にようやく直し方を変えた話です。

前作はこちら: [自動売買BOTが再起動のたびに死ぬ — journalctlの7秒差にたどり着くまで](https://zenn.dev/ponfreelance/articles/autotrader-dead-bot-loop)

## 症状は前回と同じ、場所だけ違う

2026年8月8日、デプロイのあと AI 戦略のBOTが dead になっていました。ログの時刻がきれいに揃っていました。

```
20:55:08  再起動。BOT を 900 秒間隔で再登録
21:10:08  dead 判定「31分以上応答なし」
21:10:15  初回ジョブ起動 → status=dead を見て自分を unschedule
```

**初回実行の7秒前に殺されている。** 前回と同じ7秒差でした。

数字を並べると理由がわかります。dead チェックには「サーバー起動後15分（900秒）は猶予」という保険が入っています。一方、この BOT の実行間隔は 15分（900秒）。

猶予と間隔が**同着**なのです。猶予が切れた瞬間の判定と、初回サイクルの到着が同じ時刻に並び、判定のほうが7秒早かった。

## なぜ前回の修正では防げなかったか

前回直したのは「dead から復帰させるとき」の経路でした。復帰処理が `last_run_at` を now にリセットするようにした。それは正しく効いています。

今回踏んだのは「**プロセス起動時に、running のまま再登録される**」経路です。こちらは復帰処理を通りません。status が dead ではないので、復帰の対象にすらならない。

同じ「再起動をまたいで古い `last_run_at` が残る」という現象なのに、通る道が違うだけで素通りしていました。

## その場しのぎで直しかけた

最初に思いついたのは「猶予を15分から20分に伸ばす」でした。1文字の変更で、その日は確実に直ります。

やめました。20分にしたところで、20分間隔のBOTを作った日にまた同じことが起きるからです。今回たまたま900秒対900秒だっただけで、次は1200秒対1200秒になる。数字を動かすのは、次に踏む日を先送りしているだけでした。

## 3回目だと気づいた

コミット履歴を追って、少し落ち込みました。

```
2026-04-01  fix: BOT起動時にlast_run_atを更新（dead即判定を防止）
2026-08-03  fix(main): dead BOT 自動復帰時に last_run_at をリセット
2026-08-08  fix(engine): 再起動直後に長周期 BOT が dead 判定される競合を解消
```

**3回とも同じバグです。** 4月に `routers/bots.py` で塞ぎ、8月に `main.py` で塞ぎ、また8月に `engine.py` で塞いだ。触ったファイルが毎回違います。

つまり自分は毎回「この経路を塞ぐ」という直し方をしていました。経路は塞いだそばから増えます。BOT を起動する道、復帰させる道、プロセスごと再起動する道。今後もまだあるかもしれません。

## 直し方を変えた

3回目でようやく、経路ではなく**判定そのもの**を疑いました。

dead チェックが本当に言いたいのは「この BOT はもう動いていない」です。ではその判定に必要な前提は何か。**プロセスが生きている時間より長く「応答なし」にはなり得ない。** 起動3分後のプロセスが「46分応答なし」と言うのは、そもそも成立しない主張です。

なので、判定の起点に下限を入れました。

```python
last_run = max(last_run, _engine_start_time)
```

1行です。

これで、どの経路から来ようが成立します。`last_run_at` が古いまま残っていても、プロセス起動時刻より前には遡りません。新しい起動経路が将来増えても、そこで `last_run_at` を触り忘れても、この判定は壊れない。

DB を書き換えないのも効きました。前2回は `last_run_at` の値そのものを直しに行っていたので、書き忘れた経路が抜け道になった。今回は判定側だけで閉じています。書き込みが増えないぶん、他の処理と競合する余地もありません。

ただし万能ではありません。この下限は「プロセスが起動してから経過した時間」しか見ていないので、プロセスが死なずにスケジューラだけ止まった場合は検出できます（そこは従来どおり）。逆に、再起動を繰り返して毎回15分以内に落ちるような状況では、dead 判定自体が働きません。そこは別の監視で見る前提です。

## 直ったことをどう確かめたか

「たぶん直った」で終わらせたくなかったので、回帰テストを3件書きました。再起動直後は落とさない、起動から閾値を超えて動かなければ落とす、1分間隔のBOTの検出は従来どおり。

そして運良く、デプロイ直後に**同じ条件をもう一度踏みました**。

```
21:56:50  再登録（last_run_at は 21:37:54 のまま据え置き）
22:11:50  起動猶予 900 秒が切れる
22:11:56  初回サイクル実行 ← 6秒後
```

前回は初回実行の**7秒前**に死に、今回は**6秒後**に生き残りました。ほぼ鏡写しの条件です。旧コードなら猶予切れの時点で「33.9分応答なし」となり、閾値31分を超えて確実に dead でした。

狙って作れる状況ではなかったので、これは運が良かった部分です。

## 学び

**同じバグを2回直したら、直し方を疑う。** 1回目は不運、2回目は偶然かもしれませんが、3回目は設計の問題です。自分は3回目まで気づきませんでした。

**「経路を塞ぐ」修正は、経路が増えるたびに破れる。** 塞いだ場所が正しくても、次の道が開けば同じ穴に落ちます。修正のたびに触るファイルが変わっていたら、それは経路を追いかけているサインでした。

**成立し得ない主張を弾く、という書き方がある。** 「プロセスが生きている時間より長く応答なしにはなり得ない」は、実装の詳細を知らなくても正しいと言えます。こういう不変条件で書くと、周辺のコードが変わっても壊れません。

**猶予とタイマーの長さが同じとき、順序は運任せになる。** 今回は900秒対900秒で、7秒差で負けました。保険の値を決めるときは、守りたい対象より確実に長くする必要があります。同じにすると保険になりません。

外形的には同じ症状でも、通っている道が違えば別の修正が要ります。ただ、それを何度も繰り返しているなら、道ではなく判定を見直したほうが早い。3回かかって、ようやくそう思えました。
