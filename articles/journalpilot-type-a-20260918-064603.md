月末になると、売掛金の消し込み作業に2〜3時間溶かしていないだろうか。

請求書を出した記録と、入金明細を目視で突き合わせる作業は、件数が増えるほど地獄になる。俺は個人事業主として複数の取引先とやり取りしていて、月に30件前後の請求が発生する状態で、この突合作業を手作業でやっていた時期がある。

この記事は、C言語エンジニアで副業や個人事業をやっていて、経理作業を自分でこなしている人向けに書いている。専門の経理担当がいない環境で、売掛金の消し込みを機械的にやる方法を実務目線でまとめる。

## 結論先出し

売掛金の発生・回収ペアの突合は、金額と取引先名（表記ゆれを正規化した上で）をキーにして、期間内で1対1マッチングを試みるロジックを組めば大部分は自動化できる。

完全一致しないケースゾーンは処理をスキップして、人間が見るべきリストとして吐き出すのがコツ。全部を自動化しようとすると、逆に破綻する。俺の環境では、この方式で月の消し込み作業が2時間半から15分程度まで縮んだ。

## 問題の深掘り：なぜ手作業の消し込みは破綻するか

売掛金の消し込みが手作業になりやすい理由は、会計ソフトの自動仕訳ルールが「表記の完全一致」を前提にしているケースが多いからだ。

例えば請求書には「株式会社サンプル」と書いていても、銀行明細の振込人名義は「カ）サンプル」だったり、そもそも別会社の名義（親会社経由の支払い）だったりする。金額も、振込手数料が引かれて数百円ズレることがある。この手のズレは、ルールベースの完全一致マッチングでは拾えない。

俺の場合、フリーランス期にこの手作業を3年ほど続けていて、月末になると「この入金、どの請求に対応してたっけ」と過去の請求書を遡って確認する作業が発生していた。ひどい月だと、消し込み漏れに気づかず、翌々月まで売掛金が残ったままになっていたこともある。取引先に「もう払いましたよ」と言われて初めて気づくパターンだ。これは単純に信用を落とす。

この問題を解決するために自分で作ったのが [JournalPilot](https://note.com/clab_jp/n/n4ab65a226fb1?utm_source=zenn&utm_medium=article&utm_campaign=journalpilot&utm_content=affiliflow) というツールで、マネーフォワード会計のAPIから明細と仕訳を取得して、売掛金の発生・回収サイクルを読み取り専用でチェックするスクリプトを含んでいる。今回はその中核ロジックである「突合アルゴリズム」の考え方を、汎用的な形で共有する。

## 解決手順

### ステップ1：データを正規化する前にキーを決める

まず、突合に使うキーを決める。実務では「取引先名」「金額」「期間（発生日から±60日程度）」の3つを使うことが多い。

取引先名は表記ゆれが必ず起きるので、そのまま文字列比較すると精度が落ちる。俺の実装では、全角半角統一、株式会社・（株）・カ）などの法人格表記を除去、スペース除去の3段階で正規化してから比較している。

金額は完全一致を基本にしつつ、振込手数料分（220円〜880円くらいのレンジが多い）のズレは許容する設計にした方がいい。これをやらないと、手数料が引かれた入金が全部「未消込」扱いになって、結局人間が全部見ることになる。

### ステップ2：1対1マッチングを先に試す

正規化した取引先名と金額（許容誤差込み）でグルーピングして、発生記録1件・回収記録1件のペアが取れるものを先に確定させる。ここが全体の7〜8割を占めることが多い。

俺の実データだと、月30件の売掛金のうち22〜24件はこの段階で機械的に確定した。残りの6〜8件が、金額分割・複数請求の一括入金・名義違いなどの複雑ケースになる。

### ステップ3：複雑ケースは自動処理せず、人間向けリストに出す

ここが一番大事なポイントで、1対多（複数請求を一括入金）や、名義が全く違うケースは、無理にロジックで解決しようとしない方がいい。

俺は最初、ここも全部自動化しようとして、マッチング条件をどんどん複雑にしていった時期がある。結果、条件分岐が20個近くまで膨らんで、逆に誤マッチが増えた。ある月、Aという取引先の入金をBという別の取引先の売掛金に誤って消し込んでしまい、Aの売掛金が2ヶ月分未回収のまま放置される事態になった。これに気づいたのは3ヶ月後で、修正の仕訳を4件手で入れ直す羽目になった。

この経験から、機械的に解けないケースは「保留リスト」として出力し、人間が最終判断する運用に切り替えた。自動化の目的は「全自動」ではなく「見るべき件数を減らすこと」だと割り切った方が、結果的にトータルの作業時間は短くなる。

### ステップ4：定期実行して差分だけ確認する

突合スクリプトは、毎回全件を洗い直すのではなく、前回実行時点からの差分（新規発生・新規入金）だけを処理する設計にすると実行時間が短くなる。俺の環境では、全件処理だと数十秒かかっていたのが、差分処理にしてから2〜3秒で終わるようになった。

週次で自動実行するようにしてから、月末にまとめて2時間かけていた作業が、週あたり15分程度の確認作業に分散された体感がある。

## コード例（突合ロジックの骨子）

以下はPythonでの簡略版イメージ。実際のJournalPilotはC#寄りの構成だが、ロジック自体は言語を問わない。

```python
import re
from datetime import timedelta

def normalize_name(name: str) -> str:
    # 法人格表記の除去と全角半角統一
    name = re.sub(r"(株式会社|（株）|\(株\)|カ）|カ\)|有限会社)", "", name)
    name = name.replace("　", "").replace(" ", "")
    return name.strip()

def match_records(receivables, payments, amount_tolerance=1000, date_window_days=60):
    matched = []
    unmatched_receivables = []

    for r in receivables:
        r_name = normalize_name(r["client_name"])
        candidates = [
            p for p in payments
            if normalize_name(p["payer_name"]) == r_name
            and abs(p["amount"] - r["amount"]) <= amount_tolerance
            and abs((p["date"] - r["date"]).days) <= date_window_days
            and not p.get("used", False)
        ]
        if len(candidates) == 1:
            candidates[0]["used"] = True
            matched.append((r, candidates[0]))
        else:
            # 複数候補 or 候補ゼロは人間判断行き
            unmatched_receivables.append(r)

    return matched, unmatched_receivables
```

このコードのポイントは、候補が1件に絞れないものは無理にマッチさせず、保留リストに回している点だ。候補が2件以上ある状態で自動確定させると、前述したような誤消し込みが起きる。

## 落とし穴と対処

一番踏みやすい落とし穴は、金額の許容誤差を大きく設定しすぎることだ。振込手数料のズレを吸収しようとして誤差を3000円くらいまで広げると、似た金額の別取引先の入金を誤マッチしやすくなる。俺は最初500円で始めて、手数料負けするケースが増えたので1000円まで広げたが、それ以上は広げていない。

もう一つは、期間の窓（date_window_days）を広げすぎる問題だ。60日で足りないケース（支払いサイトが長い取引先）もあるが、無理に90日、120日と広げると、たまたま金額が近い別案件と誤マッチする確率が上がる。支払いサイトが長い取引先は、個別に窓を設定する方が安全だと感じている。

あと、これは実装より運用の話だが、保留リストに出たものを放置しないルールを自分の中で決めておく必要がある。俺は「週次実行の結果、保留リストが5件を超えたらその場で処理する」というルールにしている。放置すると結局手作業の頃と同じ状態に戻る。

売掛金の消し込みは、完全自動化を目指すと誤マッチのリスクが上がる。1対1でマッチできるものだけを機械的に確定させて、残りは人間判断のリストに回す設計が、結果的に一番安定して時間を削れるという実感がある。
