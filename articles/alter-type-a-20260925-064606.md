組み込み系で長くやっていると、体調やメンタルの崩れは急に来るわけではないと分かってくる。前触れが必ずある。

食事が雑になる、歩数が減る、コードに集中できる時間が短くなる。この3つは自分の経験上、ほぼ同時に崩れ始める。それぞれ別のアプリで管理していると、この「同時性」が見えない。

本記事では、自分が実際にログを取って気づいた「崩れる3〜5日前に出るサイン」と、それをC言語で簡易的に検知するロジックの作り方を書く。個人の行動ログを多変量で見る発想は、組み込みエンジニアなら意外と馴染みやすい。

## 結論を先に書く

食事の乱れ・歩数の減少・フロー時間（集中して作業できた時間）の3指標を同じ時間軸で並べると、体調やメンタルが崩れる3〜5日前に必ず「先行して落ちる指標」がある。

自分の場合、いちばん早く落ちるのはフロー時間だった。食事や運動より2〜3日早く反応する。これは睡眠不足や疲労の蓄積が、まず集中力という一番繊細な指標に出るからだと考えている。

この記事では、3指標をローカルでログに残し、単純な移動平均と閾値判定だけで予兆を検知する方法を紹介する。統計的に高度なことはしていない。組み込みでよくやる「異常検知の前段としての閾値監視」と同じ発想でいい。

## なぜ気づきにくいのか

自分は以前、食事はあすけん、運動はスマホの歩数計、集中時間は感覚だけで管理していた。3つとも別々のアプリで、別々のタイミングで見ていた。

このとき困ったのは、「今日調子が悪い理由」を後から探そうとしても、3つのログが同じ画面に並ばないことだった。あすけんを開いて、歩数計を開いて、記憶を辿ってフロー時間を思い出す。この作業だけで10分近くかかっていた。

しかも後から振り返ると、それぞれのアプリのタイムスタンプが微妙にズレている。歩数計は0時起点、あすけんは食事のタイミング起点、記憶はさらに曖昧。3本の折れ線を同じグラフに重ねるだけで、実は結構な作業になる。

この「バラバラのログを1つの時間軸に統合する」という地味な作業が、個人の行動分析でいちばん面倒な部分だと自分は思っている。自分はこの面倒さを解消するために[ALTER](https://alter.ponfreelance.com?utm_source=zenn&utm_medium=article&utm_campaign=alter&utm_content=affiliflow)というツールを作った。食事・運動・フロー時間を1つの指標セットとして毎日記録し、同じ時間軸で振り返れるようにしている。

統合できると何が見えるようになるか。自分の場合、崩れる3〜5日前は必ずフロー時間から落ち始めていた。これは食事や歩数の記録アプリを別々に使っている間は、絶対に気づけなかった相関だ。

## 解決手順：3指標を1つのログに統合し、予兆を検知する

### ステップ1：ログのフォーマットを決める

まず1日1レコードで、以下の3つの指標を記録する形式に決めた。

```
日付,食事スコア(0-10),歩数,フロー時間(分)
2024-05-01,8,7200,180
2024-05-02,7,6800,150
2024-05-03,6,5200,90
```

食事スコアは主観評価でいい。厳密なカロリー計算より、「今日はちゃんと食べたか」の自己申告のほうが継続しやすい。自分は最初PFCバランスを細かく記録しようとして3日で挫折した経験がある。完璧な記録より、続けられる粒度を優先したほうがいい。

### ステップ2：移動平均で「いつもの自分」を定義する

1日単位の値はノイズが大きい。飲み会の翌日は食事スコアが下がるし、雨の日は歩数が減る。これを「崩れ」と誤検知しないために、直近7日の移動平均を基準値にする。

組み込みでセンサー値のノイズ除去に移動平均フィルタを使うのと同じ発想で、生活ログにも同じロジックがそのまま使える。

### ステップ3：3指標の下落が重なったタイミングを検知する

自分が実際に使っている判定ロジックはシンプルだ。

- フロー時間が7日移動平均の80%を下回った日をカウント
- 2日連続で下回ったら「注意」フラグ
- さらに食事スコアか歩数のどちらかも同時に80%を下回ったら「警戒」フラグ

この「警戒」フラグが立ったタイミングで、自分は意識的に予定を減らすようにしている。実際に去年の11月、警戒フラグが出た4日後に軽い体調不良で2日間まるごと潰れたことがあった。フラグが出た時点で仕事量を調整していれば、そこまで悪化しなかったと今は思っている。

### ステップ4：閾値は個人差があるので自分の過去データで調整する

80%という数字は自分の場合の経験値であって、万人共通ではない。最初は90%で試して、誤検知が多すぎたので80%に下げた経緯がある。過去3ヶ月分のログがあれば、実際に崩れた日の前後を見て、自分に合う閾値を逆算できる。

## 実装：C言語での簡易検知ロジック

組み込み屋らしく、外部ライブラリなしでC言語だけで書いてみる。CSVを読み込んで移動平均と閾値判定をするだけの小さなプログラムだ。

```c
#include <stdio.h>
#include <string.h>

#define WINDOW 7
#define MAX_DAYS 365

typedef struct {
    char date[11];
    double meal;
    double steps;
    double flow;
} DayLog;

double moving_average(double *arr, int idx, int window) {
    if (idx < window - 1) return -1.0; // データ不足
    double sum = 0.0;
    for (int i = idx - window + 1; i <= idx; i++) {
        sum += arr[i];
    }
    return sum / window;
}

int main(void) {
    FILE *fp = fopen("log.csv", "r");
    if (fp == NULL) {
        fprintf(stderr, "log.csv を開けなかった\n");
        return 1;
    }

    DayLog logs[MAX_DAYS];
    int n = 0;
    char line[128];

    // ヘッダ行を読み飛ばす
    fgets(line, sizeof(line), fp);

    while (fgets(line, sizeof(line), fp) != NULL && n < MAX_DAYS) {
        sscanf(line, "%10[^,],%lf,%lf,%lf",
               logs[n].date, &logs[n].meal, &logs[n].steps, &logs[n].flow);
        n++;
    }
    fclose(fp);

    double meal_arr[MAX_DAYS], steps_arr[MAX_DAYS], flow_arr[MAX_DAYS];
    for (int i = 0; i < n; i++) {
        meal_arr[i] = logs[i].meal;
        steps_arr[i] = logs[i].steps;
        flow_arr[i] = logs[i].flow;
    }

    int warning_streak = 0;

    for (int i = 0; i < n; i++) {
        double flow_avg = moving_average(flow_arr, i, WINDOW);
        double meal_avg = moving_average(meal_arr, i, WINDOW);
        double steps_avg = moving_average(steps_arr, i, WINDOW);

        if (flow_avg < 0) continue; // データ不足はスキップ

        int flow_low = logs[i].flow < flow_avg * 0.8;
        int meal_low = logs[i].meal < meal_avg * 0.8;
        int steps_low = logs[i].steps < steps_avg * 0.8;

        if (flow_low) {
            warning_streak++;
        } else {
            warning_streak = 0;
        }

        if (warning_streak >= 2 && (meal_low || steps_low)) {
            printf("%s: 警戒フラグ（フロー時間%d日連続低下、食事=%d, 歩数=%d）\n",
                   logs[i].date, warning_streak, meal_low, steps_low);
        } else if (warning_streak >= 2) {
            printf("%s: 注意フラグ（フロー時間%d日連続低下）\n",
                   logs[i].date, warning_streak);
        }
    }

    return 0;
}
```

このコードは1日分ずつログを追加してビルドし直す運用を想定している。実際にはcronで毎朝走らせて、警戒フラグが出たらSlack通知に流すところまでやっている。組み込みのログ監視バッチとほぼ同じ作りなので、この分野のエンジニアには馴染みやすいはずだ。

## 落とし穴と対処

自分が最初につまずいたのは、フロー時間の記録方法だった。ストップウォッチで正確に測ろうとして、逆に集中が途切れるという本末転倒が起きた。今は「作業を始めた時刻」と「一区切りついた時刻」だけをメモして、あとから差分を計算する方式に変えている。厳密さを追うと継続できない。

もう1つの落とし穴は、移動平均の窓を7日固定にしたことで、週末の生活リズムの違いを誤検知することがあった点だ。土日は歩数が増えて平日は減る人も多いと思う。自分の場合は逆に土日は歩数が減るタイプだったので、曜日ごとに基準値を分けたところ誤検知がかなり減った。この調整には過去データが最低1ヶ月は必要になる。

あと、3指標のうち1つでも記録を忘れる日が続くと、移動平均の窓がズレて判定精度が落ちる。自分は3日連続で記録漏れがあると、そこで一旦移動平均をリセットする処理を入れている。中途半端なデータで無理に平均を出すより、データ不足として扱ったほうが誤検知は少ない。

## まとめ

食事・運動・集中時間を別々のアプリで管理していると、崩れる前兆を見逃しやすい。自分の実感では、フロー時間がいちばん早く落ちる指標だった。
