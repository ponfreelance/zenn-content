社内ライブラリを跨いだ関数呼び出しで、呼び出し側がNULLを渡していいのか悪いのか誰も答えられない、という状況に心当たりがあるなら、この記事はそのために書いた。

自分は組み込み・制御系で23年ほどC言語を書いてきて、ライブラリ境界のNULL契約が曖昧なまま放置されているプロジェクトを何度も見てきた。ヘッダファイルにコメント1行あれば防げたクラッシュが、本番環境で発生してから調査に3日かかったこともある。

結論から書く。ヘッダファイルの関数宣言には、引数がNULLを許容するかどうかを**契約として明文化**する必要がある。コメントで書くだけでも効果はあるが、`__attribute__((nonnull))` や静的解析ツールと組み合わせることで、コンパイル時・レビュー時に機械的にチェックできる状態まで持っていくのが実務的な着地点だ。この記事では、契約の書き方、既存コードへの適用手順、そして自分が実際にハマった落とし穴を共有する。

## なぜNULL契約が曖昧になるのか

ライブラリを書いた本人は「この関数にNULLを渡すわけがない」という前提で実装している。ところが半年後、別のチームがそのライブラリを使い始めると、この前提はどこにも書かれていないので伝わらない。ヘッダファイルには関数のシグネチャだけがあって、「ptrがNULLだったらどうなるか」は実装を読まないとわからない。

自分が過去に見た例だと、ある社内共有ライブラリの`config_load()`という関数があって、第2引数の`default_conf`はNULLでもいい設計だった。しかし別の関数`config_merge()`は同じような見た目なのに、第2引数がNULLだと即座にクラッシュする実装になっていた。呼び出し側のエンジニアは「同じライブラリの関数だから同じ規約だろう」と類推して、後者にもNULLを渡してしまった。結果、本番投入後3週間目に間欠的にクラッシュが発生し、原因特定に丸2日かかった。

この手のバグが厄介なのは、L0（コンパイラ警告ゼロ）を通していても検出できない点にある。コンパイラは「NULLを渡してはいけない」というルールを知らないので、警告のしようがない。cppcheckやclang-tidyにNULLチェックのルールを設定していても、契約が文書化されていない関数に対しては何も指摘できない。ツールは「ここにルールがある」と教えられて初めて機能する。ルールそのものが存在しない状態では、静的解析も無力になる。

この「契約が実装者の頭の中にしかない」問題は、自分がずっと悩んでいたところで、解決の糸口を探しているうちに[CSAF](https://autotrader.booth.pm/items/8163116?utm_source=zenn&utm_medium=article&utm_campaign=csaf&utm_content=affiliflow)というツールを自作するに至った。CWE-476（NULLポインタ参照）やCWE-457（未初期化変数の使用）を区別して検出する仕組みを作る過程で、まず契約を書く文化がないと検出も意味を持たないという当たり前の事実に何度も突き当たった。

## 解決手順：NULL契約を書いて検証可能にする

### ステップ1：既存のヘッダを棚卸しする

まず、社内で共有しているヘッダファイルのうち、ポインタ引数を持つ関数を洗い出す。自分がやったときは、あるプロジェクトで約340関数のうち、ポインタ引数を持つものが210関数あった。そのうちNULL許容/非許容が明示されていたのは12関数だけだった。ドキュメント化率にすると6%弱で、これが実態だと思っていい水準だ。

棚卸しの際は、grepで`*`を含む引数を持つ関数宣言を抽出し、CSVなどに一覧化する作業から始めるのが現実的だ。数百関数規模なら半日、数千関数規模なら1〜2週間の見積もりになる。

### ステップ2：契約をコメント規約として決める

次に、NULL許容の契約を書くフォーマットを決める。自分のチームでは以下のような規約にした。

```c
/**
 * @param conf   設定構造体へのポインタ。NULL不可。
 * @param logger ロガーへのポインタ。NULL可（NULL時は標準エラー出力にフォールバック）。
 */
int app_init(const config_t *conf, logger_t *logger);
```

「NULL不可」「NULL可」という2値だけでなく、NULL可の場合に何が起きるかまで書くのがポイントだ。「NULL可」とだけ書いてあっても、呼び出し側は結局実装を読みに行くことになるので、契約を書く意味が半減する。

### ステップ3：機械的にチェックできる形に落とす

コメントは人間には読めるが、コンパイラやCIには読めない。ここで`__attribute__((nonnull))`を使うと、NULL不可の契約をコンパイラに教えられる。

```c
int app_init(const config_t *conf, logger_t *logger)
    __attribute__((nonnull(1)));
```

これで第1引数にNULLを渡すコードに対して、GCC/Clangが警告を出すようになる。ただし、この属性だけでは実行時のNULLチェックは行われない点に注意がいる。あくまでコンパイラの静的解析を補強する仕組みであって、防御的プログラミングの代わりにはならない。

自分の経験では、`__attribute__((nonnull))`を既存の200関数規模のヘッダに一気に付けると、隠れていたNULL渡しの箇所が十数件、警告として一気に浮上することが多い。最初の導入時は警告の洪水になるので、優先度の高い外部公開APIから順に適用していくやり方が現実的だ。

### ステップ4：レビューのチェックリストに組み込む

契約を書く文化を根付かせるには、コードレビューのチェックリストに「新規追加した公開関数にNULL契約のコメントがあるか」を1項目加えるのが効果がある。自分のチームでは、この1項目を追加してから、レビューでの指摘漏れによる本番障害が半年で0件になった。ただしこれは母数が小さいプロジェクトでの数字なので、規模が大きい現場では別の効果測定が必要になるかもしれない。

## コード例：契約とチェックの組み合わせ

実際にヘッダとチェックの両方を書いた例を示す。

```c
// logger.h
/**
 * ログメッセージを出力する。
 * @param msg  出力する文字列。NULL不可。渡された場合は呼び出し側のバグ。
 * @param tag  ログのタグ文字列。NULL可（NULL時は"default"扱い）。
 * @return 成功時0、失敗時-1。
 */
int log_write(const char *msg, const char *tag)
    __attribute__((nonnull(1)));
```

```c
// logger.c
int log_write(const char *msg, const char *tag) {
    const char *effective_tag = (tag != NULL) ? tag : "default";
    // msgはnonnull属性で契約済みだが、
    // 防御としてassertも残しておく
    assert(msg != NULL);

    fprintf(stderr, "[%s] %s\n", effective_tag, msg);
    return 0;
}
```

ここで大事なのは、`__attribute__((nonnull))`をつけたからといってassertを外さないという点だ。属性はコンパイル時の静的チェックであって、実行時に不正な値が来る可能性（例えば関数ポインタ経由の呼び出しやキャスト経由の呼び出し）まではカバーしない。二重の防御として残しておくのが実務では安全だと感じている。

## 落とし穴と対処

自分が実際にハマった点を3つ挙げる。

1つ目は、`__attribute__((nonnull))`を既存コードに機械的に付けた結果、テストコード側でNULLを渡すテストケースがコンパイルエラーではなく警告止まりになり、CIで見逃されたことがあった。`-Werror`と組み合わせないと、この属性は実質的に効果を持たない。自分の環境では`-Wall -Wextra -Werror=nonnull`まで指定して、ようやくCIで確実に落ちるようになった。

2つ目は、契約コメントを書く際に「NULL可」と書いたつもりが、実装側が途中でNULLチェックを削除するリファクタリングをしてしまい、契約と実装が乖離したケースだ。これはコメントとコードが物理的に離れているために起きる問題で、契約を書いたら終わりではなく、実装変更のたびにヘッダも見直す運用ルールが必要になる。自分のチームでは、ヘッダとソースを同じPRで変更する際に「契約変更あり」のラベルを付ける運用にして、レビュアーが気付きやすくした。

3つ目は、サードパーティ製ライブラリのヘッダには当然この契約が書かれていないので、自社ラッパーを一枚挟んで契約を明示する作業が発生したことだ。この作業自体は地味だが、ラッパー層を1つ挟むだけで、少なくとも自社コード内でのNULL関連バグは大きく減らせた実感がある。

## 関連ツール

ヘッダの契約チェックやNULL関連のCWE検出を手作業でやり続けるのは現実的ではないと感じたので、自分は[CSAF](https://autotrader.booth.pm/items/8163116?utm_source=zenn&utm_medium=article&utm_campaign=csaf&utm_content=affiliflow)というツールを作った。CWE-457（未初期化変数）とCWE-665（不適切な初期化）の取り違えや、sizeof on pointerのdecay/明示の混同といった、現場でよく起きる誤検出・見逃しパターンを正確に区別することを狙ったツールで、完全ローカル動作なので社外にコードを出せない医療・車載・組み込み系のプロジェクトでも導入しやすい構成にしてある。無料版のcreviewから段階的に試せるようにもしているので、契約の文書化とあわせて検討してもらえたらと思う。

## まとめ

ヘッダのNULL契約は、書いたその日には誰も感謝してくれない地味な作業だ。ただ、契約が書かれていない関数は半年後、1年後に必ず誰かを詰まらせる。自分の経験では、契約コメント＋`__attribute__((nonnull))`＋レビューチェックリストの3点セットで、本番でのNULL関連クラッシュはかなり減らせるという実感がある。まずは自分のプロジェクトの公開ヘッダを1つ棚卸しするところから始めてみてほしい。
