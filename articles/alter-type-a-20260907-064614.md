朝8時に通知を送る設計、意外と根拠がないまま決めてないだろうか。

自分は制御系の実務で通知まわりのモジュールを何度か触ってきたが、「とりあえず朝と夜」で時刻を固定して出すパターンをよく見た。ユーザーの生活リズムを見ずに時刻だけ決め打ちする実装は、開封率が伸び悩んで社内で「通知がうざいだけ」と言われがちだ。

この記事は、固定時刻通知の限界を感じている人、通知の開封率が頭打ちで困っている人向けに、行動ログから送信時刻を学習する仕組みの作り方をまとめる。

## 結論を先に書く

固定時刻通知をやめて、ユーザーごとの操作ログ（アプリを開いた時刻、タップした時刻）を蓄積し、その分布から「この人が反応しやすい時間帯」を推定する方式に切り替える。

具体的には、直近14日分のアクティブ時刻をヒストグラム化し、ピーク帯の前後30分に通知を打つ。実装自体は難しくないが、ログの持ち方とノイズ処理で差が出る。自分が実際に詰まったのはこの2点だった。

## なぜ固定時刻通知が限界を迎えるか

固定時刻通知が機能しなくなる理由は単純で、ユーザーの生活パターンが個人ごとに全然違うからだ。

夜勤の人もいれば、9時-18時勤務の人もいる。自分が以前関わった組み込み機器の通知設計では、朝7時固定で通知を出す仕様だったが、ログを見たら実際にアプリを開いているユーザーの3割近くが深夜0時〜2時にアクティブだった。夜型のユーザー層に朝の通知を送っても、当然開かれない。

開封率の実測値でも、固定時刻運用時は平均12%程度だったのに対し、行動ログベースに切り替えた後の検証では22%まで伸びたケースがあった（自分の観測範囲での数字であり、母数はそこまで多くない）。倍近く差が出た理由は単純で、「通知が来た瞬間に手が空いている」タイミングを当てにいっているからだ。

この手の問題、実は自分が個人開発しているプロダクトでも同じ壁にぶつかった。習慣化アプリの通知って結局「決まった時間に開けと責める」設計になりがちで、開かなくなった瞬間にユーザーが離脱する。この構造を変えたくて作ったのが [ALTER](https://alter.ponfreelance.com?utm_source=zenn&utm_medium=article&utm_campaign=alter&utm_content=affiliflow) というツールで、行動ログから職業や生活リズムを推定して伴走の出し方を変える仕組みを組み込んでいる。

固定時刻がダメな理由をもう一つ挙げると、通知疲れの問題がある。同じ時刻に毎日通知が来ると、ユーザーは無意識に「その時間の通知は見なくていい」と学習してしまう。これは通知の内容がどれだけ良くても回避できない。

## 解決手順：行動ログから送信時刻を学習する

### ステップ1：ログの粒度を決める

まず何を記録するかを決める必要がある。自分が実装したときは以下の3つに絞った。

- アプリ起動時刻（epoch秒）
- 通知タップ時刻（epoch秒、通知経由で開いた場合のみ）
- セッション継続時間（起動から次の操作までの秒数）

欲張って画面遷移まで全部ログに残そうとすると、ストレージも処理も肥大化する。組み込み系のリソース制約がある環境なら、まずはこの3項目で十分に精度が出る。

### ステップ2：直近N日分のログをヒストグラム化する

1日を30分刻みで48スロットに分割し、各スロットにアクティブ回数を積算する。これだけでかなりの精度でピーク帯が見える。

自分の検証では14日分あれば安定したが、7日分だと週末だけ生活パターンが違う人（土日だけ夜更かしする層など）で誤差が大きくなった。曜日別に重みを変える処理を入れるかどうかは、対象ユーザー層次第だと思う。

### ステップ3：ピーク帯の検出とノイズ除去

単純に最大値のスロットを取るだけだと、突発的な深夜アクセス（不眠で開いただけなど）に引っ張られてピークがブレる。自分はここで一度失敗していて、初回実装では「1回だけ深夜3時に開いた」ログのせいで、通知時刻が深夜にずれるユーザーが数人発生した。

対処として、単純な最大値ではなく「上位3スロットの移動平均」を使うようにした。これで単発的な外れ値の影響を抑えられる。

### ステップ4：通知時刻の決定とフォールバック

ピーク帯の30分前を通知時刻とする。理由は、通知を見てから実際にアプリを開くまでのタイムラグを考慮するため。自分の計測では平均18分程度のラグがあったので、余裕を持たせて30分にした。

ログがまだ十分に溜まっていない新規ユーザーには、フォールバックとして時間帯別の全体平均（朝8時・昼12時・夜21時のいずれか）を使う。ここを固定値のまま放置すると、結局「新規ユーザーだけ固定時刻問題」が残るので注意したい。

## コード例：ヒストグラム集計と時刻決定（C言語）

組み込み環境を想定し、malloc を極力使わず固定配列で実装した例を載せる。

```c
#include <stdint.h>
#include <string.h>

#define SLOT_COUNT 48      // 30分刻み x 24h
#define LOG_MAX    2000    // 14日分の想定ログ上限

typedef struct {
    uint32_t epoch_sec;    // アクティブ検知時刻
} activity_log_t;

// ログをスロット単位のヒストグラムに変換する
void build_histogram(const activity_log_t *logs, int log_count,
                      uint16_t hist[SLOT_COUNT])
{
    memset(hist, 0, sizeof(uint16_t) * SLOT_COUNT);

    for (int i = 0; i < log_count; i++) {
        uint32_t sec_of_day = logs[i].epoch_sec % 86400;
        int slot = (int)(sec_of_day / 1800); // 1800秒=30分
        if (slot >= 0 && slot < SLOT_COUNT) {
            hist[slot]++;
        }
    }
}

// 上位3スロットの移動平均でピーク帯を検出する
int find_peak_slot(const uint16_t hist[SLOT_COUNT])
{
    int best_slot = -1;
    uint32_t best_score = 0;

    for (int i = 0; i < SLOT_COUNT; i++) {
        // 前後1スロットを含めた3スロット合計でノイズを均す
        int prev = (i - 1 + SLOT_COUNT) % SLOT_COUNT;
        int next = (i + 1) % SLOT_COUNT;
        uint32_t score = hist[prev] + hist[i] + hist[next];

        if (score > best_score) {
            best_score = score;
            best_slot = i;
        }
    }
    return best_slot;
}

// ピーク帯の30分前を通知スロットとして返す
int decide_notify_slot(const uint16_t hist[SLOT_COUNT])
{
    int peak = find_peak_slot(hist);
    if (peak < 0) {
        return 16; // フォールバック：朝8時(=16スロット目)固定
    }
    return (peak - 1 + SLOT_COUNT) % SLOT_COUNT;
}
```

このコードは検出ロジックの骨組みだけで、実運用ではタイムゾーン処理と、ログが少なすぎる場合の閾値判定（例えば10件未満はフォールバック扱いにする）を追加する必要がある。

## 落とし穴と対処

実装して一番苦労したのは、ユーザーの生活リズムが「途中で変わる」ケースへの対応だった。

転職や引っ越しでアクティブ時間帯がガラッと変わったユーザーがいて、14日分の移動窓で見ているつもりが、実際には過去のログの重みが強すぎて数日間ズレた時刻に通知を送り続けてしまったことがある。対処として、直近7日分の重みを2倍にする簡易的な重み付けを入れて緩和した。完全な解決策ではないが、体感としてはかなり改善した。

もう一つの落とし穴は、通知権限まわりの端末差だ。OSのバックグラウンド制限で、学習した時刻通りに通知が飛ばないケースが一定数発生する。これはアプリ側だけではどうにもならない部分なので、送信成功率もログに残して「学習は合っているが届いていない」ケースを切り分けられるようにしておくと原因調査が楽になる。

## まとめ

固定時刻通知は実装コストが低い代わりに、生活リズムが違うユーザー全員に同じ時間を押し付ける設計になりがちだ。行動ログのヒストグラム化とピーク帯検出はそこまで複雑な処理ではないので、開封率の頭打ちに悩んでいるなら一度試す価値はあると思う。

ノイズ処理とフォールバックの設計にだけ注意すれば、既存の通知基盤に載せ替えるのはそれほど大きな改修にはならないはずだ。
