Zaifやbitbank初期のAPIみたいに、取引所側に逆指値（ストップロス）注文の機能が無いケースがある。国内APIをいくつか触ったことがある人なら、一度はこの壁にぶつかったことがあるはずだ。

自分もbot実装を始めた頃、逆指値が無い取引所に当たって手が止まった。この記事では、取引所APIに依存しない疑似ロスカットの作り方を、実際に動かした実装ベースで書く。

結論から言うと、価格監視をポーリングでやりつつ、約定価格からの下落率をトリガーにして市場注文（もしくは成行に近い注文）を撃つ仕組みを自前で作る。取引所側の機能に頼らず、自分のプロセス内で監視ループを持つのが基本方針になる。実装の肝は「監視間隔」「約定確認の遅延」「二重発注の防止」の3つで、ここを丁寧に作らないと本番で事故る。

## なぜ逆指値が無いと詰まるのか

取引所APIのドキュメントを読むと、成行・指値はあるのに逆指値（stop order）が存在しないパターンが普通にある。特に国内のマイナー取引所や、bitFlyerでも一部のプロダクトAPIでは提供されていない時期があった。

これに気づかず実装を始めると、最初は「注文タイプにSTOPが無いだけだろう」と軽く見て、後から気づいて設計をやり直すことになる。自分は最初、注文APIのenumを見て「そのうち増えるだろう」くらいに考えていたが、結局増えなかった。

問題は逆指値が無いことそのものより、「ロスカットの責任が自分のプロセスに移る」という点だ。取引所がやってくれない以上、価格監視・トリガー判定・発注の全部を自分のコードで持つ必要がある。プロセスが落ちたらロスカットも止まる。ここに気づかずに実装すると、監視サーバーが再起動している数分の間にポジションが無防備になる、みたいな事故につながる。

## 解決手順

### ステップ1：ポーリング間隔を決める

まず現在価格をどの間隔で取得するか決める。多くの取引所はRate Limitがあるので、1秒間隔でticker APIを叩くと簡単に制限に引っかかる。

自分がbitFlyerで検証したときは、public APIのticker取得を3秒間隔にして、複数ペア監視でも余裕を持って動いた。逆に1秒間隔にしたところ、10分程度でHTTP 429が返ってきた。取引所ごとにRate Limitの仕様が違うので、まずは公式ドキュメントの制限値を確認して、その半分以下の頻度で叩くくらいの余裕を持たせるのが安全だと思う。

### ステップ2：トリガー条件を決める

ロスカットのトリガーは「約定価格からの下落率」で持つのが実装しやすい。例えば、購入価格の3%下落でロスカット、というルールをコードに落とす。

ここで気をつけたいのは「最新価格1回だけ」でトリガーしないこと。取引所のtickerは一瞬だけ異常値を返すことがある。自分は過去に、bitFlyerのtickerが一瞬だけ極端な値を返して、誤発注に近い動きをしたことがあった。以降は直近3回分の価格を見て、3回連続で条件を満たしたときだけ発注する、という形にしている。

### ステップ3：発注と二重発注防止

トリガーが発火したら注文APIを呼ぶが、ここで一番事故りやすいのが二重発注だ。監視ループが3秒間隔で動いていると、注文APIのレスポンスが遅延している間にもう一度トリガー判定が走り、同じポジションに対して2回発注してしまうことがある。

自分の実装では、発注前にポジション状態をローカルのステータス（`ORDER_PENDING`など）で管理して、pending中は次のトリガー判定をスキップするようにしている。これをやらずに最初のバージョンを動かしたときは、同じポジションに対して2回市場注文が飛んで、想定より多く売る事故を起こした。金額としては数千円レベルの実損だったが、ロジックの根本的な作り直しになった。

### ステップ4：プロセス監視を分離する

ロスカットの監視ループ自体が落ちたら意味が無いので、監視プロセスは取引ロジックとは別プロセスで動かして、ヘルスチェックを別途持つ構成にしている。自分はRailway上でPostgreSQLと監視ワーカーを分離して、ワーカーが5分応答しなかったらアラートをDiscordに飛ばす仕組みを入れている。

## コード例（Python / FastAPI想定）

```python
import time
from decimal import Decimal

class PseudoStopLoss:
    def __init__(self, entry_price: Decimal, stop_rate: Decimal = Decimal("0.03")):
        self.entry_price = entry_price
        self.stop_price = entry_price * (1 - stop_rate)
        self.price_history = []
        self.status = "WATCHING"  # WATCHING / ORDER_PENDING / CLOSED

    def check(self, current_price: Decimal) -> bool:
        if self.status != "WATCHING":
            return False

        self.price_history.append(current_price)
        if len(self.price_history) > 3:
            self.price_history.pop(0)

        # 直近3回連続で閾値を下回ったときだけ発火させる
        if len(self.price_history) == 3 and all(
            p <= self.stop_price for p in self.price_history
        ):
            self.status = "ORDER_PENDING"
            return True
        return False

    def mark_closed(self):
        self.status = "CLOSED"
```

このクラスをポーリングループから3秒おきに`check()`で呼び、`True`が返ったタイミングだけ市場注文APIを叩く。`ORDER_PENDING`に入っている間は判定自体をスキップするので、発注APIのレスポンス待ちの間に再発火する事故を防げる。

## 落とし穴と対処

一番踏みやすい落とし穴は、Rate Limit対策で監視間隔を伸ばしすぎることだ。3秒を10秒に伸ばすと、急落局面でロスカットの発動が数秒〜十数秒遅れて、想定より深い価格で約定することがある。自分の検証では、1分間で5%動くような急変動時に、10秒間隔だと想定価格より1.5%くらい不利な価格で決済されたことがあった。

もう一つは、約定確認のタイミングだ。発注APIが200を返してきても、実際の約定はその後数百ms〜数秒かかる取引所がある。発注直後にすぐ次の判定ループへ進んでしまうと、未約定のポジションに対してもう一度ロスカット判定が走ることがある。自分は発注後、約定確認APIで`filled`ステータスを取れるまでpendingを維持する形にして、この問題を潰した。

NDAの範囲で言えるのはここまでだが、取引所ごとに約定確認のレスポンス形式が違うので、5取引所分を実装すると地味に時間を食う作業になる。自分は1取引所あたり実装+検証で2〜3日くらいかかった実感がある。
