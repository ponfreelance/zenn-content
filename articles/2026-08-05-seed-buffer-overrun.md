C言語23年、自分はフリーランスで組み込み・サーバサイド両方のコードレビューに入ることが多いです。

去年、あるチームのCIに静的解析を組み込む相談を受けました。ツール導入自体は半日で終わるのですが、厄介なのは「どのタイミングで何を落とすか」の設計です。最初の提案では creview の重大判定を全部 CI で fail させる案を出したところ、初日で既存コードの警告が200件出て運用が止まりました。原因は単純で、L0（コンパイラ警告）を素通りしたレガシーコードに creview をいきなり当てたからです。今回はその反省を踏まえて、L0からL3までの段階運用をどう設計したかを、実際に検出した11件のバッファオーバーフロー系コードで具体的に書きます。

## SCQA

- **状況**: CI に静的解析ツールを1本追加するだけなら簡単ですが、「重大判定は全部ブロック」という運用は初日で破綻しがちです。既存コードの負債と新規PRの品質基準を同じゲートで扱うと、どちらかが機能しなくなります。
- **問題**: creview のようなツールは検出精度が高い分、既存コードに対して大量の指摘を出します。これを全部 CI でブロックすると、レガシー資産を持つチームは初日でパイプラインが赤くなり、誰も直さないまま `--force` でマージする文化が生まれます。
- **問い**: 新規PRの品質は厳格に守りつつ、既存コードの負債と衝突しない CI ゲート設計はどう組めばいいのか？
- **答え**: L0（コンパイラ警告ゼロ）を絶対条件にした上で、creview は `--preset pr` で diff 範囲のみに絞り、既存コードの負債は CSAF で別枠の監査レポートとして切り離す、という3層構成にしました。

## L0: まずコンパイラ警告を全部潰す

creview の話に入る前に、`-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）または `-Wall -Wextra -Werror -Weverything`（Clang）を有効にしてビルドが通るか確認してください。NULL引数をnonnull関数に渡す、未初期化auto変数を読む、戻り値を破棄する、自明なNULL deref、use-after-free、境界外配列アクセス（静的決定可なもの）、switch case抜け。これらは現代のコンパイラが標準で拾います。

自分が今回相談を受けたチームでも、実は今回の検証コードにある `sizeof(p)` の誤用（CWE-467）は `-Wsizeof-pointer-div` 相当の警告でclangが拾えるケースがあります。ここをL0でスクリーニングせずにcreviewだけに頼ると、コンパイラで無料で取れる指摘までcreviewのレポートに混ざって、レビュー担当者が「これはコンパイラ警告？creview固有？」と毎回判定するコストが発生します。

これらが警告ゼロにならないPRは、creviewを走らせる前にそもそもレビュー対象にしないルールにしてしまうのが第一手です。CIのジョブ順序としては「L0ビルド警告チェック → 失敗ならここで停止 → 通過したものだけcreviewへ」という直列構成にしました。

## 検証用コード

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* スタックバッファのオーバーフロー（strcpy + sizeof 誤用） */
void copy_name(const char *src) {
    char buf[16];
    strcpy(buf, src);                    /* 検出すべき: 長さ未検証 */
    printf("name=%s\n", buf);
}

/* sprintf による境界未検証 */
void format_path(const char *dir, const char *file) {
    char path[32];
    sprintf(path, "%s/%s", dir, file);   /* 検出すべき: snprintf を使うべき */
}

/* sizeof(ptr) ハマりパターン */
void wipe_buffer(char *p) {
    memset(p, 0, sizeof(p));             /* 検出すべき: sizeof(p) は常に 8（ポインタサイズ） */
}

/* 配列インデックス未検証（scanf 入力をそのまま添字に） */
void read_at(int *arr) {
    int i;
    scanf("%d", &i);
    printf("%d\n", arr[i]);              /* 検出すべき: i の上下限チェック無し */
}
```

## CWE/MISRA マッピング

| 検出箇所 | パターン | CWE | 事故の形 |
|---------|---------|-----|---------|
| L6, L13, L19, L24 | NULL契約未表明（nonnull属性なし） | CWE-476 周辺 | 呼び出し側がNULLを渡した場合、コンパイル時に検知できず実行時クラッシュに直結 |
| L7, L14 | マジックナンバー（16, 32のバッファサイズ） | CWE-547 | サイズ変更時に複数箇所を手動同期する必要があり、1箇所直し忘れでオーバーフロー再発 |
| L8 | strcpy使用 | CWE-121 | コピー元の長さがコピー先を超えるとスタック上のリターンアドレスまで書き換わる典型的なスタックオーバーフロー |
| L15 | sprintf使用 | CWE-121 | dir/fileの合計長がpath[32]を超えるとオーバーフロー。snprintfなら第2引数で上限を強制できる |
| L20（前段） | pのNULL未検証でmemset実行 | CWE-476 | NULLポインタへの書き込みでSEGV。組み込みならハードフォルトで即死 |
| L20（後段） | sizeof(p)を配列長として誤用 | CWE-467 | 関数パラメータのポインタはdecayしているため、sizeof(p)は常にポインタサイズ（4/8byte）を返し、意図したバッファ長にならない |
| L27 | 外部入力を境界チェックなしで配列添字に使用 | CWE-129 | scanfで受けた値がそのまま添字になり、範囲外読み取り（CWE-125）や書き込みに繋がる入口 |

L7とL14のマジックナンバーは、allowlist `{-1, 0, 1, 2}` 以外の整数リテラルを機械的に全部flagしています。malloc引数だけでなく配列宣言の`[16]`や`[32]`もcontextとして検出対象にしているのがポイントで、以前別のツールでmalloc引数しか見ていないルールに当たって、配列宣言側のサイズ変更が漏れる事故を見たことがあるので、このあたりは検出ルールの網羅性を最初に確認しておくべきところです。

3段階ラベルの読み方は以下の通りです。

- **【重大】**: CWEに直結する実害パターン。CIでは原則マージブロック対象。今回の11件は全部これに該当します。
- **【設計不明】**: 意図的な設計なのかミスなのか機械では判定できないもの。例えばグローバル変数の共有方式など。CIではブロックせず、レビュアーへのコメント表示に留めます。
- **【保守危険】**: 今すぐ壊れないが将来の変更で壊れやすい箇所。マジックナンバーの一部はここに分類されることもありますが、今回はバッファサイズ直結のため【重大】に格上げしています。

このプロジェクトでは、CIパイプラインの設定として「【重大】が1件でもあればmergeブロック、【設計不明】と【保守危険】はコメント投稿のみでブロックしない」という閾値をJSON設定で持たせました。最初は全部ブロックにしていましたが、リリース直前の週に【保守危険】判定で足止めされて、結局`--severity-threshold critical`だけに絞る変更を入れた経緯があります。ここは一度全部厳しくしてから緩める順序の方が、チームの納得感を得やすいと感じました。

## 3段階の使い分け

| 場面 | 使うツール | 使いどころ |
|------|-----------|-----------|
| L0: ビルド時（まずここ） | gcc / clang の警告 + `-Werror` | `-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）/ `-Weverything -Werror`（Clang）。警告ゼロにならないPRはそもそもレビューに入らないルール化 |
| L1: PRチェック | clang-tidy / cppcheck | OSSの主流チェックをCIで強制 |
| L2: PRレビュー | creview（CLI・自社プロダクト） | プロジェクト固有パターン、日本語ナレッジ、severityモデル（重大/設計不明/保守危険）、CWE/MISRAマッピング、`--preset pr`でdiffのみ |
| L2': 自己チェック（PR投げる前） | c-review-ai（ブラウザ版・自社プロダクト） | 環境構築不要、コピペで試せる軽量版。今回のような検証コードを投げるだけで動作確認できる |
| L3: チーム監査・MISRA準拠 | CSAF（自社プロダクト） | libclang AST + 依存グラフでrisk A/B/C自動昇格。既存コードの負債はここで棚卸し |

運用ルールとして固定しているのは「L0の警告がゼロにならないPRはレビューに入らない」をCIで強制する点です。L0を素通りしたPRをcreviewで叩いても、消せた警告まで人間が読むことになって意味がありません。実際、最初にこの順序を逆にしていたチームでは、creviewの指摘の3割がclangの標準警告で消せるものだったという集計結果が出ています。

CIのジョブ構成としては、PRトリガーで L0（ビルド） → L1（cppcheck）→ L2（creview `--preset pr` でdiffのみ）を直列実行し、mainブランチへのマージ後に週次でCSAFの監査ジョブを別途走らせる形にしました。既存コードの負債（今回でいえばL7・L14のマジックナンバーのような大量検出パターン）をPRゲートに混ぜないことが、パイプラインを止めない最大のポイントです。

## まとめ

- L0（コンパイラ警告ゼロ）を通過しないPRはcreviewの対象にしない。ここを飛ばすと重複指摘でレビュアーが消耗する
- `sizeof(p)`の誤用（CWE-467）はパラメータのポインタdecayが原因で、配列宣言のsizeofとは挙動が違う点をチーム全員に周知しておく
- マジックナンバー検出はmalloc引数だけでなく配列宣言も対象にし、allowlist外を機械的に全部拾うルールで統一する
- PRゲートは`--preset pr`でdiff範囲のみに絞り、既存コードの負債はCSAFの週次監査に分離してCIを止めない設計にする
- severity閾値は最初厳しく設定してから緩める順序の方が、チームの合意形成がしやすい

### 試すリンク（無料で試す → 業務で監査する）

C言語の静的解析を、いきなり有料ではなく「無料で手を動かす → 日常運用 → 監査レベル」の順で用意しています。

- **まずブラウザで試す → c-review-ai**（自社プロダクト / MIT / 無料）
  貼り付けた1ファイルをその場でレビュー。導入ゼロで挙動を確かめる用。
  → https://cutt.ly/1yuTys1c
- **CLI で日常運用 → creview**（自社プロダクト / 無料）
  手元のコードをコミット前に単発チェック。CI にも組み込める。
  → https://cutt.ly/syuTpB7z
- **リポジトリ全体を監査 → CSAF**（自社プロダクト / ¥4,980 買い切り）
  MISRA 準拠チェックと CWE データフロー解析をリポジトリ横断で走らせ、監査レポート（HTML）を出力。
  レビューの属人化を止めたいチーム向けで、商用の静的解析ツールなら数十万円かかる基本機能を、個人でも入れられる価格にしています。
  → https://cutt.ly/ItKo4MPY

無料の2つで「使える」と感じたら、リポジトリ全体に監査を回すのが CSAF です。バージョンは随時更新しています。
