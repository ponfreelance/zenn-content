C言語23年、自分はフリーランスで組み込みのコードレビューに入ることが多いです。

先週も似たようなPRを見ました。`malloc` の戻り値を使う直前のコード、レビューで見た瞬間に「あ、これ本番のメモリ逼迫時にだけ落ちるやつだ」と分かるのに、テストは全部通っている。CIも緑。レビューワが集中力を切らした金曜の午後に来ると、正直見逃します。この記事は「malloc/calloc/realloc戻り値未チェック」というマージ前レビューで一番見逃しやすいパターンを、どういう視点でチェックすれば拾えるか、creviewでの実検証を通して書きます。

## この記事の前提（SCQA）

- **状況**: メモリ確保のコードは書いた瞬間は動きます。開発機はメモリが潤沢なので `malloc` が失敗するケースは滅多に再現しません。
- **問題**: レビューワは「動くコード」を見て「正しいコード」と錯覚しがちです。NULLチェック漏れは実行パスとして通常運転では発火しないため、レビューでもテストでも素通りしやすいです。
- **問い**: マージ前レビューで、実行しないと分からない失敗パスをどう可視化するか？
- **答え**: 静的解析で「malloc系関数の戻り値を使う手前にNULLチェック分岐があるか」を機械的に検証し、レビューワの目視チェックリストから外してしまう。人間は「そのNULLチェック後の復旧ロジックが妥当か」という設計判断だけに集中する。

## L0: まずコンパイラ警告を全部潰す

creviewの話に入る前に、`-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）または `-Wall -Wextra -Werror -Weverything`（Clang）を有効にしてビルドが通るか確認してください。未初期化auto変数を読む、戻り値を破棄する、自明なNULL deref、use-after-free、境界外配列アクセス（静的決定可なもの）、switch case抜け、これらは現代のコンパイラが標準で拾います。

実際、今回の検証コードを `gcc -Wall -Wextra -fanalyzer` に通すと `-fanalyzer` が `load_user()` の `u->id = id` あたりで「possible NULL dereference」系の診断を出すケースがあります（バージョンとオプション次第で検出精度は変わります）。ここで拾えるものをcreviewに二重に頼る必要はありません。

**これらが警告ゼロにならないPRは、creviewを走らせる前にそもそもレビュー対象にしないルールにしてしまうのが第一手です。** L0を素通りしたPRをL2で叩いても、消せた警告まで人間が読むことになって意味がありません。

## 検証用コード

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* malloc 戻り値未チェックで即 use する典型 */
struct user {
    int id;
    char name[64];
};

void load_user(int id) {
    struct user *u = malloc(sizeof(*u));
    u->id = id;                          /* 検出すべき: NULL チェック無し */
    strcpy(u->name, "anonymous");        /* 検出すべき: NULL チェック無し */
    printf("user=%d name=%s\n", u->id, u->name);
    free(u);
}

/* calloc も同パターン */
int *make_table(size_t n) {
    int *p = calloc(n, sizeof(int));
    p[0] = 1;                            /* 検出すべき: NULL チェック無し */
    return p;
}

/* realloc の罠（戻り値を元ポインタに再代入して NULL チェックなし） */
void grow_buffer(char **buf, size_t *cap) {
    *cap *= 2;
    *buf = realloc(*buf, *cap);          /* 検出すべき: realloc が NULL を返したら元ポインタも失う */
    (*buf)[0] = '\0';                    /* 検出すべき: NULL deref 可能 */
}
```

`load_user()` は `id` を引数で受け取っているのに、creviewは「7行目で宣言、初期化なし」の未初期化変数として `id` を指摘しています。一見誤検出に見えますが、実際に読むと `load_user(int id)` の `id` は引数であり初期化済みです。ここはツールの誤検知パターンとして注記しておきます（後述のログ解説で触れます）。creviewの出力を鵜呑みにせず、レビューワが1件ずつ「これは本当に危険か」を判断する必要がある実例として、そのまま載せます。

## CWE/MISRA マッピング

| 検出パターン | CWE | 事故の形 |
|------------|-----|---------|
| malloc/calloc/realloc 戻り値未チェック（L12, L21, L29） | CWE-690 | メモリ逼迫時に `malloc` がNULLを返し、直後のメンバアクセスでNULL deref。組み込みではヒープ枯渇が起きやすく、再現性は低いのに発火すると即クラッシュ |
| NULLポインタ参照そのもの（L12, L21, L27, L29） | CWE-476 | `u->id = id` のようにNULL構造体へのメンバアクセスでSIGSEGV |
| realloc戻り値を元ポインタに直接代入（L27） | CWE-476（元ポインタ喪失によるリーク併発） | `*buf = realloc(*buf, *cap)` がNULLを返すと元の `*buf` の参照を失い、メモリリーク＋直後のdeaf落ちが同時発生 |
| strcpyでのバッファオーバーフロー（L14） | CWE-121 | コピー元文字列長を検証していないため、固定長 `name[64]` を超える入力でスタック破壊 |
| free後にNULL代入しない（L16） | CWE-416（UAFの温床） | `free(u)` 後 `u` がdangling pointerのまま残り、後続コードで誤って再アクセスするとuse-after-free |
| マジックナンバー64（L8） | CWE-547 | バッファサイズがハードコードされ、他箇所のサイズ変更時に不整合が生まれてオーバーフローの原因になる |
| grow_bufferでのNULL契約未表明（L27） | CWE-476周辺 | `buf` が非NULLである契約が関数シグネチャに現れておらず、呼び出し側のミスがコンパイル時に検出できない |

## creview の使い方（CLI 実行例）

```bash
creview review load_user.c --preset memory --format markdown
```

```
L8 【重大】: マジックナンバー64 (バッファサイズ) — allowlist 外。#define / enum / .creviewrc.json で命名 or 許可
L11 【重大】: 未初期化変数idを使用(7行目で宣言、初期化なし)。不定値
L12 【重大】: uにNULLチェックなし。malloc/calloc/realloc失敗時クラッシュ
L14 【重大】: strcpy使用。コピー元長未検証でオーバーフロー可能
L16 【保守危険】: free(u)直後にNULL代入なし。dangling pointer残存
L20 【保守危険】: 関数make_table()の宣言・定義がファイル内に見つからない。ヘッダinclude漏れまたはリンクエラーの可能性
L21 【重大】: pにNULLチェックなし。malloc/calloc/realloc失敗時クラッシュ
L27 【重大】: ATTR-NONNULL-001: grow_buffer() の buf を NULL 検査せず使用。__attribute__((nonnull(N))) で契約を明示するか、関数先頭で NULL 検査して return
L29 【重大】: bufにNULLチェックなし。malloc/calloc/realloc失敗時クラッシュ
```

3段階ラベルの読み方は次の通りです。

- **【重大】**: 実行時クラッシュ・メモリ破壊・未定義動作に直結する指摘。マージ前に必ず修正が必要。今回9件中7件がこれに該当。
- **【設計不明】**: 今回の検出には出ていませんが、「意図が読み取れない実装」に付くラベル。関数責務やAPI契約が曖昧な箇所に使われます。
- **【保守危険】**: 今すぐ落ちないが、将来の変更や別の開発者の手で事故を誘発するもの。`free`後のNULL代入漏れや関数定義未検出（L20）がこれに該当。

L11とL20は、実運用でハマったポイントです。L11の「未初期化変数id」は誤検出で、`id`は引数なので初期化済みです。creviewの静的解析ルールが「宣言行と初期化行が同一かどうか」を見る際、関数引数を宣言と誤認識するケースがあると分かりました。L20の「make_table()の定義が見つからない」も、実際には同一ファイル内に定義されているのにcreviewが検出できていない誤検知です。単一ファイルの断片コードを解析対象にした際の既知の制約で、プロジェクト全体をコンテキストとして渡す `--preset pr` 実行では解消される見込みです。ツールの出力を鵜呑みにせず「なぜこの行がこの指摘になったか」を1件ずつ確認する作業は、結局人間のレビューワの仕事として残ります。

## 3段階の使い分け

| 場面 | 使うツール | 使いどころ |
|------|-----------|-----------|
| L0: ビルド時（まずここ） | gcc / clang の警告 + `-Werror` | `-Wall -Wextra -Wpedantic -Werror -fanalyzer`（GCC）/ `-Weverything -Werror`（Clang）。警告ゼロにならないPRはそもそもレビューに入らないルール化 |
| L1: PRチェック | clang-tidy / cppcheck | OSSの主流チェックをCIで強制 |
| L2: PRレビュー | creview（CLI、自社プロダクト） | プロジェクト固有パターン、日本語ナレッジ、severityモデル（重大/設計不明/保守危険）、CWE/MISRAマッピング、`--preset pr` でdiffのみ、AI補強 |
| L2': 自己チェック（PR投げる前） | c-review-ai（ブラウザ版、自社プロダクト） | 環境構築不要、コピペで試せる軽量版 |
| L3: チーム監査・MISRA準拠 | CSAF（自社プロダクト） | libclang ASTと依存グラフでrisk A/B/C自動昇格 |

**運用ルール**: 「L0の警告がゼロにならないPRはレビューに入らない」をCIで強制する。L0を素通りしたPRをcreviewで叩いても、消せた警告まで人間が読むことになって意味がありません。今回の検証コードも `-fanalyzer` である程度拾えるため、creviewの役割は「コンパイラが見逃す部分、かつプロジェクト固有の危険パターン」に絞る運用が現実的です。

## まとめ

- malloc/calloc/realloc戻り値未チェックは、開発機では発火せず本番のメモリ逼迫時にだけ落ちるため、レビューでもテストでも見逃されやすい。
- 今回の検証では9件中7件が【重大】に分類され、いずれもCWE-476/CWE-690に該当する実行時クラッシュ系の指摘だった。
- creviewの出力は完璧ではない。今回もL11（未初期化変数の誤検知）とL20（関数定義未検出の誤検知）の2件で人間の判断が必要だった。
- reallocを元ポインタへ直接再代入するパターン（`*buf = realloc(*buf, *cap)`）はNULL返却時に元ポインタも失うため、一時変数を経由する書き方への修正が必須。
- L0（コンパイラ警告ゼロ）を通過したPRに対してだけcreviewを走らせる運用にしないと、重複指摘の読み込みコストが無駄に増える。
