自分で作ったサービスを運用していて、壊れたデータに気づくのがユーザーからの問い合わせの後になっている人向けの記事。外部キーや NOT NULL では守れない「値同士の関係」を、夜間バッチで全ユーザー分まとめて検査する方法を書く。

この記事は設計と手順の解説で、検知件数や運用実績の数字は載せていない。SQL とテーブル名は説明用の例。

## 結論先出し

- 不変条件は「違反している行を返す SELECT」として1条件1ファイルで書く。0行なら正常。
- 夜間の全件検査は、読み取り専用トランザクションでスナップショットを固定し、cutoff 時刻より古い行だけを対象にする。これが誤検知を止める1つ目の仕掛け。
- 違反が出たら少し待って再検査し、2回連続で出たものだけを通知する。これが2つ目。
- 通知は前回との差分（新規違反）だけにする。同じ違反を毎晩通知しない。

## 問題の深掘り

データベースの制約で守れるのは、NULL かどうか、参照先があるか、一意かといった単純な条件までになる。次のような条件は、アプリケーションが正しく動くことを前提にしている。

- ユーザーの累計値が、元になった行動ログの合計と一致している
- 体力のような値が 0 以上、上限以下に収まっている
- 同じユーザーの同じ日の記録が1件しかない
- 累計値が前日より減っていない

これらはバグ、マイグレーションの取りこぼし、本番での手動修正のどれでも崩れる。しかも崩れたこと自体は画面にエラーとして出ない。数字が少しずれたまま動き続け、ユーザーが気づいて初めて分かる。

組み込みの assert や CRC チェックと同じ発想で、運用中のデータにも定期的に整合性を問い合わせる仕組みを置いておくと、発見までの時間が短くなる。

題材になるのは、指標を行動ログから積み上げるタイプのサービスだ。自分が作っている [ALTER](https://alter.ponfreelance.com?utm_source=zenn&utm_medium=article&utm_campaign=alter&utm_content=affiliflow) は、食事=MP、運動=HP、フロー時間=EXP、副業=CHA という指標マッピングを持っていて、ログと指標の関係がある構造なので、この種の検査が当てはまる領域だと考えている。ただし、以降の条件と SQL は説明用の設計例で、ALTER の実運用値や検知実績ではない。

夜間バッチで検査するときの難しさは、検査の正しさより誤検知にある。誤検知が続くと通知が読まれなくなり、検査自体が形骸化する。以降はそこを重点的に書く。

## 解決手順

### 手順1：不変条件を文章で書き出す

まず日本語で書き出す。SQL にするのはその後。

1. 累計 EXP は、確定済みログの EXP 合計と一致する
2. HP は 0 以上 hp_max 以下
3. 同一ユーザー・同一日の朝活記録は1件
4. 累計 EXP は前回スナップショットより減らない

### 手順2：1条件を1つの SELECT にする

違反行を返すクエリにして、`checks/` ディレクトリに1条件1ファイルで置く。1列目はキー（user_id など）に揃える。後続の再検査と差分通知で、1列目をそのまま使えるようにするため。

### 手順3：スナップショットと cutoff で1つ目の誤検知を止める

アプリが「ログを INSERT」と「累計を UPDATE」を別トランザクションで行っている場合、その2つの間の瞬間は、スナップショットを固定しても不整合に見える。夜間でも書き込みは止まらないので、検査が当たると誤検知になる。

対策は、検査対象を cutoff 時刻（実行時刻の30分前など）より前に確定した行だけに絞ること。更新途中の行は、検査対象に入らない。

### 手順4：再検査で2つ目の誤検知を止める

cutoff を入れても、遅延したジョブや再試行中の処理で、一時的な不整合が残ることはある。そこで、違反が出たらしばらく待ち、新しい cutoff でもう一度同じ検査をして、両方に出たキーだけを確定違反とする。

一時的な不整合なら、待っている間に解消されて2回目には出ない。バグによる恒常的な不整合なら、2回とも出る。

### 手順5：通知は差分だけにする

確定違反の集合を保存しておき、前回の集合との差分（新規に増えたキー）だけを通知する。同じ違反を毎晩通知すると、数日で誰も見なくなる。

## コード

違反行を返す SQL の例。累計 EXP とログ合計の不一致を調べる（`checks/total_exp_mismatch.sql`）。

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout = '120s';

SELECT u.id AS user_id,
       u.total_exp,
       COALESCE(SUM(l.exp), 0) AS log_exp
FROM users u
LEFT JOIN action_logs l
       ON l.user_id = u.id
      AND l.created_at < :cutoff
WHERE u.updated_at < :cutoff
GROUP BY u.id, u.total_exp
HAVING u.total_exp <> COALESCE(SUM(l.exp), 0);

COMMIT;
```

範囲チェックは単純に書ける（`checks/hp_out_of_range.sql`）。

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SET LOCAL statement_timeout = '120s';

SELECT id AS user_id, hp, hp_max
FROM users
WHERE updated_at < :cutoff
  AND (hp < 0 OR hp > hp_max);

COMMIT;
```

実行側のシェルスクリプトの例。二重起動防止、2回検査、差分通知までをまとめている。

```bash
#!/usr/bin/env bash
set -euo pipefail

exec 9>/var/lock/invariant_check.lock
flock -n 9 || { echo "already running"; exit 0; }

WORK=$(mktemp -d)
STATE=/var/lib/invariant_check
mkdir -p "$STATE"

run_pass() {  # $1 = first|second
  local cutoff
  cutoff=$(date -u -d '30 minutes ago' '+%Y-%m-%d %H:%M:%S')
  for f in checks/*.sql; do
    name=$(basename "$f" .sql)
    psql "$DATABASE_URL" -X -At -v ON_ERROR_STOP=1 \
         -v cutoff="'$cutoff'" -f "$f" \
      | cut -d'|' -f1 | sort -u > "$WORK/$name.$1"
  done
}

run_pass first
sleep 600
run_pass second

for f in checks/*.sql; do
  name=$(basename "$f" .sql)
  comm -12 "$WORK/$name.first" "$WORK/$name.second" > "$WORK/$name.confirmed"
  touch "$STATE/$name.prev"
  comm -13 "$STATE/$name.prev" "$WORK/$name.confirmed" > "$WORK/$name.new"
  if [ -s "$WORK/$name.new" ]; then
    ./notify.sh "$name" "$WORK/$name.new"
  fi
  cp "$WORK/$name.confirmed" "$STATE/$name.prev"
done

date -u '+%s' > "$STATE/last_success"
```

cron の登録は、負荷の低い時間帯に1行入れるだけ。

```
15 3 * * * cd /opt/invariant_check && ./run.sh >> /var/log/invariant_check.log 2>&1
```

## 落とし穴と対処

ここに書くのは設計上起こりやすい問題で、特定の実体験ではない。

**全件検査が本番を遅くする。** 読み取りレプリカで実行するか、本番なら `statement_timeout` を必ず設定し、ユーザー ID の範囲でチャンクに分けて流す。サンプルの120秒はあくまで例で、自分のデータ量に合わせて決める。

**条件を追加した初日に違反が大量に出る。** 過去データにすでに違反が含まれているため。初回は通知せず、現状をベースラインとして `prev` に保存してから、翌日以降の差分だけ通知する。

**cron が止まっていることに気づかない。** 違反ゼロの通知は来ないので、止まっても静かなまま。上のスクリプトは最後に `last_success` を書いている。別の監視から、この時刻が26時間以上古ければ通知するようにしておく。

**検査が長引いて翌日と重なる。** `flock -n` で二重起動を防ぐ。重なって実行されなかった日は `last_success` が更新されないので、上の監視で拾える。

**検知と修復を同じスクリプトに入れる。** 自動修復は、原因がバグだった場合にバグごと隠してしまう。検知は検知、修復は人が原因を見てからにしたほうが安全だと考えている。

**時刻の扱い。** cutoff は UTC で統一する。サーバーのローカル時刻と DB の時刻が混ざると、境界付近の行で誤検知が出る。
